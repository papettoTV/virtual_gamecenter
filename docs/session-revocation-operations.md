# セッション失効RPC：警告集計・通知・復旧

対象：検証Pages / `pulbase-staging`。本番導入・長時間負荷試験は含まない。

## 検知

ログアウトはD1のセッション削除が成功してから、各筐体DOへ失効RPCを送る。一過性障害は最大3回、過負荷・恒久障害は再試行しない。RPCが未完了でもD1の失効は取り消さず、ゲストへの切替を完了する。旧セッションは次の認可確認で拒否するが、無通信ソケットの即時一斉切断は保証しない。

検証専用 `SECURITY_EVENTS` バインディングから既存 `pulbase_service_health` にログアウト1回につき1点を記録する。追加の外部API・Cron・DB書込みはない。

| 項目 | 内容 |
| --- | --- |
| index1 | `staging-revocation` |
| blob1 / blob2 / blob3 | `staging` / `rooms` または `directory` / `revocation-v1` |
| double1 | 未完了ログアウトなら1、成功なら0（筐体一覧取得失敗を含む） |
| double2 / double3 / double4 | 未完了筐体数 / 対象筐体数 / 追加再試行数 |

利用者ID・筐体ID・セッションハッシュ・Cookie・IP・生の例外文は集計へ保存しない。`directory` 失敗時の筐体数0は「対象なし」ではなく「不明」。ログの `session_revocation_incomplete` / `session_revocation_retry` と併用する。記録失敗は固定文言 `session_revocation_metrics_failed`。集計障害でログアウトを失敗させないため、集計はベストエフォートであり、無警告だけで安全を判定しない。

## 通知条件

既存のサービス死活通知1枠（ID `0677e7f471c44e79adf07c6bacc40b37`）に統合。費用/R2の6通知と利用量の4通知は維持する。5分評価・値1以上・15分再通知・Cloudflare登録メールのまま。設定の正は `apps/web/config/service-alerts.json`。

| 値 | 状態・運用 |
| --- | --- |
| 0 | 条件非該当。失効復旧の証明ではない |
| 1 | 既存のサービスDOWN |
| 2 | 既存のサービスRECOVERED。失効RPCの復旧ではない |
| 3 | 20分間、死活監視の記録なし。失効イベントで欠落を埋めない |
| 4 | 20分間に失効未完了が1件以上。少数でも調査する |
| 5 | 20分間に追加再試行10回以上。単発で復旧した一過性障害は通知しない |

優先順位は3→1→4→5→2。メール1通で全症状を列挙する方式ではない。上位警告が出た際も下位の集計とログを調査する。失敗後の別利用者の成功で失敗を打ち消さない。20分後の条件解消は「新しい警告なし」であり、旧ソケットの切断完了を意味しない。

Analytics Engineのサンプリング重み `sampleInterval` で件数を推計する。厳密な課金台帳・失効ジョブの永続キューではない。高頻度時の間引きや取り込み遅延、メール評価・再通知待ちを考慮する。全体を止める自動処理は追加しない。

## 復旧手順

1. メール値と現在の集計・構造化ログを確認。対象は検証Workerであることを照合し、発生時刻・`directory`/`rooms`・失敗数・再試行数・直前のデプロイ版を記録する。秘密の値をインシデント資料に貼らない。
2. D1/DOの障害・過負荷とCloudflareの障害情報を確認。D1削除失敗によるHTTP 5xxは別障害として扱い、ログアウト成功と決めつけない。過負荷時に全筐体へ無制限の失効RPCを再送しない。
3. 設定・コードが原因なら前版との互換性を確認し検証Workerだけを修正/巻き戻す。DBのセッションを復活させたり、認可チェックを無効化したりしない。デプロイ後はクエリ除去設定を再適用する（`cloudflare-log-privacy.md`）。
4. 専用テスト利用者で接続→ログアウトを短時間に1回実施。旧セッションで本人API/クレジット予約が拒否され、旧WebSocketからの操作が1008で閉じられ、匿名観戦は継続することを確認する。共通RPC処理の障害注入回帰テストと3ゲームの失効競合テストも実行する。実利用者のCookieは取得しない。
5. 既に失効済みのアイドル接続はこの確認だけでは切断済みにならない。ユーザーが操作すれば認可で拒否される。継続障害・疑わしい操作・即時全切断が必要な場合は運営判断で利用停止へ進める。既存検証/本番には停止・全DO再失効の運営機構が未導入なので、隔離DO訓練だけを根拠に一斉切断済みと報告しない。導入と全体停止は別途承認する。
6. 警告発生後20分以上の観測、新規の正常ログアウト集計、旧資格情報の拒否を確認して記録する。メール停止だけで完了としない。発生/復旧時刻・確認項目・影響・残ったアイドル接続リスクを残す。

## 確認コマンド

`apps/web` で実行。ローカルの `.dev.vars` はGit対象外・モード600を維持する。

```sh
node scripts/verify-revocation-alert.mjs --environment staging
npx vitest run tests/worker/logout-failure.test.ts tests/worker/revocation-metrics.test.ts
npm test
```

SQL検証は合成した集計値で12個のCASE分岐を確認し、最後に実データの集約SQLを読み取る。合成の障害点を書き込んだり、実利用中のDOを壊したりする処理ではない。SQL APIではサブクエリ/定数だけの表生成が利用できないため、分岐検証と実データの集計検証を区別する。

参照：[Analytics Engine集計関数](https://developers.cloudflare.com/analytics/analytics-engine/sql-reference/aggregate-functions/)、[SQL API](https://developers.cloudflare.com/analytics/sql-api/)。
