# ゲーム開始要求・受信確認と正式な月間SLO

更新：2026-10-21。実装・検証はdevelop / pulbase-stagingのみ。本番・main・通知条件・長時間負荷試験の状態は変更しない。

## 測定対象と目標

正式SLIは「認証・所有予約の確認後、クレジット確定要求をD1へ永続受理した時点から、開始許可を受信したクライアントの確認がサーバーへ戻るまで」。目標は日本時間の暦月で98%以上。実際の描画開始、ゲーム内のREADY解除、FPS、ボタンクリックからの全体時間とは異なる。

| 開始方法 | 受信確認の期限 | 成功条件 |
| --- | --- | --- |
| 新しいクレジットを使うソロ開始 | 受理から5秒 | 正しい接続から開始許可の確認が1件戻る |
| 新しいクレジットを使う対戦/再戦 | 受理から30秒 | 両参加接続から、それぞれ異なる席の確認が戻る |

- 分母は受理した一意の予約件数から、消費不成立の明確な業務拒否を除いた件数。HTTP再送・二重確定・重複ACKで増やさない。
- クレジット処理の技術例外、開始メッセージ未到達、DO起動/セッション確認/許可処理の障害、許可後の切断・確認未到達は、期限までに許可受信が確認できなければ失敗となる。
- `missing_response` は「開始許可の期限内ACKがない」こと。HTTPエラー応答が返った場合も含み、物理的な完全無応答だけを指す言葉ではない。
- 受理後の中断・ログアウトや、期限超過後にようやく始まったケースも、保守的に失敗に含める。遅延したACKで過去の失敗を成功に書き換えない。返却の既存業務ルールは変更しない。
- 認証前/予約照合前/永続受理前の通信・DB障害、残高不足、不正な予約はこのSLIの分母外。無料の勝者継続・切断復帰等、新しい確定要求を伴わない開始も分母外。これらを含むサービス全体の開始成功率とは呼ばず、死活監視や将来の別SLIで扱う。
- 未改変の公式クライアントによる許可パケットの受信確認であり、画面描画や人間によるプレイの証明・不正スコアの防止ではない。

## 要求と結果を失わない仕組み

移行`0022_start_slo.sql`で、短期間の`start_slo_attempts`、識別子を持たない`start_slo_daily`、計測開始メタデータ、15分スロットの`start_slo_coverage`を追加した。

1. stagingのcaptureで、クレジット消費のトランザクションより前に要求を独立して永続化。消費がロールバックされても受理済み要求は残る。記録自体が失敗した場合は消費へ進まず、受理成功とも扱わない。
2. DOが既存の予約/セッション/参加権限検証と状態保存を済ませ、`allowed_ms`を記録してから、参加者にだけランダムな照合値を付けて開始許可を送る。
3. 3ゲーム共通の`CabinetClient`が`soloStarted` / `versusCountdown`をデコードし、同じ接続で`startReceipt`を返す。旧接続・観戦フレームは対象にしない。ACK送信障害で本来のゲームメッセージ処理を止めない。
4. DOは、その接続に割り当てた照合値・席、現在のセッションと権限を確認。別の観客や参加者以外が値を知っても他の席として確認できない。DBの条件付き更新で重複を排除する。
5. トリガーが要求・許可・確定を日別に加算する。集計値と詳細状態は同じD1トランザクションで変化する。

期限切れは毎時保守で確定するが、運営者が見る集計では未確定の期限切れもその場で失敗に加算する。保守Cronが止まっても、pendingを除外して成功率を上げない。複数のSELECTをD1 batchの同一トランザクションで読み、確定/未確定を二重加算しない。

詳細の削除時にもpendingは失敗へ加算してから消す。退会・予約削除で分母が消えたり成功率が上がったりしない。開始計測用の障害が、既存の削除保守を実行しない理由にもならない（保守は継続し、計測の保守エラーは別途失敗として返す）。

## 正式判定の条件

運営者画面`/operator/operations`と既存JSON APIに、今月と先月のD1実件数を表示する。従来のAnalytics Engine推計とは混ぜない。判定は丸め前の件数で行い、表示上の小数点以下2桁で判定しない。

| 判定 | 条件 |
| --- | --- |
| 計測開始待ち | まだ受理済み要求がない |
| 計測期間不足 | 月初より後に計測を開始/再開した |
| 集計中（月/確定待ち） | 月未終了、または月終了後10分以内 |
| 未確定データあり | 成功/欠落/除外へ整合していない要求が残る |
| 計測の欠測あり | 必要な15分チェックが1件でも欠ける |
| 判定対象なし | 観測期間が揃っても、対象要求が0件 |
| 達成 / 未達 | 上記の不確定条件がなく、成功/対象件数が98%以上 / 未満 |

月はJSTの1日0時から翌月1日0時（未満）。要求を受けた月に帰属し、月をまたぐ確認でも期限内なら元の月の成功となる。対戦の最大30秒と監視記録の実行遅延を吸収するため、月終了後10分は確定を待つ。

既存の15分Cronを共用し、新しいCron式は作らない。1日最大96スロットを記録する。毎時のクレジット/削除保守とは独立し、Analytics Engine APIの成否にも依存しない。未来時刻、10分を超える遅配や過去の穴埋めは受け付けず、同じスロットは1件だけ保存する。

2026-10-21 08:00 JSTの初回実行は、正時ちょうどだけを受け付けた実装が失敗した。保存ログにはscheduledTime `1792537225.599`、例外時刻 `1792537226644`があり、起動に秒/ミリ秒差があることを確認。時刻単位と15分境界を正規化する修正と、実値を使う回帰テストを追加した。初回の欠測を後から正常記録で埋めない。

## 保存・復旧

- 詳細は受信期限から2日経過後の毎時保守で削除。予約ID・一時照合値は保護対象。外部AEへこれらを送らない。元の予約台帳・通常アクセスログの期間は既存方針と別である。
- 個人/予約/筐体IDを持たない日別件数・監視スロットは400日を目安に日単位/時刻単位で削除。計測開始時刻は継続判定の運用メタデータとして保持する。
- 新しいCookie・DB外サービス・Secretは追加しない。既存プライバシーのゲーム/障害調査目的と保持期限を補足し、GA同意とは独立した必要なゲーム通信として扱う。法務・公開判断全体の完了を意味しない。
- D1復元・計測停止・旧版へのロールバックで欠測の可能性が生じたら、運営者はcoverage_started_msを復旧後の時刻へ更新し、その月を計測期間不足に戻す。復元した古いカウンターの見かけの率だけで達成としない。過去のチェック記録を手入力して埋める運用は禁止する。

## 検証手順と範囲

`scripts/verify-start-slo-staging.mjs --environment staging`は宛先・DB名をstagingへ固定し、合成ゲストだけを使う短時間の機能確認。負荷試験ではない。既存Google利用者の消費・付与・ログアウト、実購入、本番操作は行わない。最後に自分の全接続を閉じる。繰り返しで無料枠や付与制限を消費しないよう、必要な変更時だけ実施する。

初回07:55 JSTの実通信で次を確認した：

- 3ゲームのソロ許可・受信確認成功と、匿名観戦へのフレーム配送。
- capture再送が同じ要求1件のままであること。
- 開始WSメッセージを送らなかった要求、許可は受けたがACKを返さなかった要求が、それぞれ期限切れになること。
- 観客から盗用値でACKしても反映されず、正規の接続でも遅延ACKは成功へ戻らないこと。
- DOT WAVE対戦で片方のACKだけではpending、両方のACKで成功し、重複ACKでも件数が増えないこと。

## 残る運用課題

- 欠測なしの暦月を実際に観測し、正式判定を確認すること。実装済みと98%達成済みは別である。
- 未受理のHTTP/ネットワーク障害、無料継続、実画面の開始までの別SLI、復元運用への計測再開手順の組込み。
- D1のSLO欠落を既存通知へ統合する運用。コード6等のAE通知条件は今回変更しない。
- 本番の環境別導入と承認、外部独立監視、同時障害の分類別回復。長時間負荷試験は保留・未合格。
