# 深海サルベージの退出時Close調査

Issue #132の記録では、stagingのPages経由でネイティブWebSocketを閉じる4条件すべてが約10秒後に1006、wasClean=falseとなった。互換日は自動返信に対応する日付であり、古い互換日を原因とは判断していない。

ソース上、Pages gatewayとWorkerの筐体ルートは101レスポンスをそのまま返す。CabinetRoomの受信Closeハンドラーには明示返信がなく、DB処理とadmission解放のみがあった。今回、非同期の退出処理より先にCloseへ返信する。通常退出・筐体変更のクライアントCloseには1000を指定する。これは明示返信が経路上で必要という仮説への最小修正で、stagingの原因を確定したものではない。

leaveCabinet自体は接続を閉じない。共有クライアントのleave、深海サルベージの再参加、GRAZE DUEL、DOT WAVE、SDKの退出経路と、Workerの再join時に内部leaveを呼ぶ経路を確認した。同一接続の再joinを維持する。既存のvisitor判定による退出の冪等性、切断時のsolo復旧、認可失敗の1008、予約のrelease、capture、admission解放は変更しない。

回帰テストは実WorkerのClose返信、観戦の継続、同一接続の再joinと、ブラウザでのleave有無×Closeコード有無を検査する。通常の空Closeはランタイムの自動返信なら1005、明示返信なら1000を許容するが、必ずwasClean=trueを要求する。アプリの退出では1000を要求し、残高・予約/capture/release件数・スクロール復帰の既存検査も維持する。1006は成功に含めない。

ローカルではWorker集中テストとnpm testがlisten EPERMで起動できなかった。UI実行用Playwright依存もなく、ブラウザケースは未実行。build:stagingは成功。Pagesゲートウェイの実Service Binding経路はこの環境では再現・検証できず、デプロイもしていない。最新stagingで4条件とアプリ退出の実Closeイベント、接続解放・会計、および実機ノッチ表示を再確認するまで受け入れ条件は未完了。
