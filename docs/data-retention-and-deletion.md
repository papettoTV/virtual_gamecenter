# PULBASE データ保存と削除・退会方針

版：2026-10-12。対象：無料クレジット制ベータ。保存期間は法定期間を一律に表すものではなく、サービス運営上の方針である。

## 原則

残高・ハイスコアなど長く遊ぶための資産は利用中保持する。調査・流入計測の個別情報には期限を設ける。本人が退会・ゲスト削除を確定したら公開・認証を停止し、通常データは原則30日以内に削除する。Cookieの期限とサーバー保存期間は別である。

## 保存期間

| 対象 | 期限と起算点 |
| --- | --- |
| 登録プロフィール、Google連携、残高 | 利用中。退会後30日以内に削除。長期未利用アカウントは年1回必要性を見直し、アクセスがないだけで自動消去しない |
| ゲスト情報・無料残高 | 最終セッション利用から1年。登録・購入記録のある利用者はこの自動削除から除外 |
| 認証セッション | 有効期限まで。ログアウトしたセッション、退会した全セッションは即時失効 |
| 無料台帳、終了済みのプレイ/仮確保履歴 | 発生・終了から1年。残高と特典資格は別途保持。未完了・既存購入関連は自動削除しない |
| 日次補充記録 | 補充日から90日。当日と重複防止記録は保持 |
| ランキング・共有結果 | ゲーム提供中。本人の公開記録削除・退会で削除。終了ゲームは終了日から1年以内に削除 |
| 筐体・観戦同期 | 全接続終了後24時間以内。退会時は対象者の接続・状態を除去。長期映像保存はしない |
| 分散乱用対策の制限キー・予算 | IP/利用者IDのハッシュと当日/当分の件数。期限はUTCの翌日/翌分、次の5分回収で削除。接続枠は接続終了時に返却し、失敗時は筐体との再照合で回収。稼働中の接続情報と直近24時間の筐体割当は上限管理に必要な間保持。障害中の回収遅延を完了扱いにしない |
| 個別の共有・観戦流入イベント | 発生から90日。長期分析が必要なら個人・筐体・共有IDへ戻せない集計へ変更してから保存 |
| 通常アクセス/障害ログ | 原則30日以内。Cloudflare等の実際の設定・契約と一致させる。既存の外部保存をアプリ内処理で削除できたと扱わない |
| 開始SLOの詳細照合記録 | 開始許可の受信期限から2日経過後の毎時保守で削除。予約ID・一時確認値を保護し、予約削除にも連動する。受信未確認のまま削除しても失敗件数へ算入し分母を消さない |
| 開始SLOの日別件数・15分チェック | 個人・予約・筐体IDを持たない集計と時刻のみ。400日経過後の毎時保守で削除。退会しても個別へ戻す照合キーのない集計は保持。初回の計測開始時刻は継続判定用の運用メタデータとして保持 |
| 開始応答欠落通知の1分バケット | 個人・予約・筐体IDのない要求/拒否/欠落の件数。受信期限の分から2日経過後の毎時保守で削除。初期導入時刻は監視窓の判定用メタデータとして保持。外部の通知記録・AE保存期間とは別 |
| 問い合わせ | 対応完了から1年。X側の記録を運営者が完全に消せるとは案内しない |
| 規約同意・削除処理の最小証跡 | 退会/削除完了から1年。本人に直接結び付く情報・本文は不要な範囲を除去 |
| 特典受取済みの照合値 | 付与から最大5年。端末/登録特典の再取得防止に限定し、名前・メール・Google識別子原文は残さない。ハッシュを匿名情報と断定しない。期限後の永久的な重複防止は保証しない |
| 既存の実決済 | 自動削除から除外。税務・紛争対応等の必要期間と残高処理を個別に確認 |
| バックアップ | D1 Time Travelの契約上の期間（現在Free 7日 / Paid 30日）。独自定期エクスポートは追加しない。隔離した復元訓練では合成データだけを一時SQLへ出力し、実データのバックアップとは分けて扱う |

## 削除手順

1. プロフィールから「退会・データ削除」（登録済み）または「ゲストデータを削除」を開く。名前・残高・削除対象・例外を確認する。
2. 登録者はGoogleで同一アカウントを再確認する。ローカルのみ開発者再認証を使える。ゲストは有効な利用セッションで確認する。名前やXアカウントだけで本人判定しない。
3. サーバー発行の確認情報と明示的な確認操作で受付する。本人はリクエスト本文の任意のプレイヤーIDではなくセッションから決める。別Originからの操作を拒否する。
4. 購入残高・未完了の購入などがある場合は自動削除を受け付けず、窓口で個別対応する。
5. 受付時点で対象を削除中にし、全セッション・公開記録を停止する。処理途中で失敗しても新しい登録・公開書込みはできない。
6. 筐体接続・Durable Objectの情報、関連する個別計測、公開結果、ランキング、プレイ/台帳/プロフィールを削除する。特典受取済み照合と最小証跡だけ分離して残す。
7. 冪等な削除ジョブで再試行する。画面には受付番号と完了/処理中を表示する。受付情報の閲覧用秘密値はURLに載せない。
8. このブラウザのPULBASE用localStorage/sessionStorageを削除する。別端末の保存情報は遠隔消去できないが、認証はすべて失効する。端末識別Cookieは特典再取得防止のため維持する。

ランキング/共有だけを削除する操作も提供する。プロフィール・残高は維持する。退会のようにGoogle再確認を必要とする。

## 復元と例外

削除済み情報がバックアップに期限まで残ること、外部SNSの投稿・画像キャッシュ・第三者の保存が残り得ることを説明する。復元時は独立した非公開R2の削除受付記録を照合して削除を再適用し、確認完了まで一般利用へ戻さない。削除記録を同じD1だけに置いてTime Travelで巻き戻す運用は禁止する。R2には受付ID・対象内部プレイヤーID・スコープ・受付確認用照合値・期限を1年保存する。原文の名前・メール・Google識別子は含めないが、内部IDも保護対象として扱う。R2が利用できない場合は削除を新規受付せず、受付後の失敗は処理中として再試行する。本番R2の設定・実際の復元手順の検証は公開前の運営作業である。

不正・紛争調査で保存を延長する場合は対象・理由・担当者・期限を記録し、原則90日ごとに見直す。通常データを理由なく一括延長しない。本人の請求には法令に従って個別判断し、例外の理由を案内する。

## 実装・運用の境界

アプリ内D1/筐体データの削除と期限処理を実装する。Google Analytics、Cloudflareログ、X DMの保持設定・個別削除、独自バックアップ、専門家への法務確認は外部設定・運用であり別途検証する。全データが自動で30日以内に消えると宣言しない。

2026-10-20：検証Workerの要求URLのクエリ除去を有効化し、ログ収集・保存は維持した。Workers標準ログとPagesリアルタイムログの保持仕様・閲覧権限の点検結果は[Cloudflareログの保護](cloudflare-log-privacy.md)を参照。保存ログの実効性確認と運営者認証の本人対応は残る。既存ログの遡及マスキング・削除を完了したとは扱わない。

従来のランキングには所有者IDがない。名前で所有者を推測しない。所有者未確定の旧レコードは公開から除外して保全し、移行時に別途確認する。一律の期限で既存ハイスコアを消さず、所有者の確認後に移行・個別削除する。公開前に未帰属レコードを確認し、保全を長期に放置しない。自動削除の完了は所有者を確認できた対象についての完了である。新しいランキングはプレイヤーID・結果IDを必ず保存する。

## 実装と検証

- 所有者と特典資格を分離するマイグレーション：`0019_data_lifecycle.sql`。購入と削除の競合防止：`0020_deletion_purchase_guard.sql`。
- API：`GET /api/platform/data-deletion/preview?scope=all|public`、`POST /api/platform/data-deletion/request`、`GET /api/platform/data-deletion/{受付ID}`（確認用秘密値は`X-Deletion-Receipt`ヘッダー）。対象IDは有効なセッションから決める。
- Google再確認：`/api/platform/auth/reauth`。OAuthで異なるGoogleアカウントが返った場合は拒否する。開発者アカウントの再確認はローカル/プライベートネットワークでのみ許可する。
- UI：プロフィールから退会/ゲスト削除・公開記録だけの削除・受付状況を選べる。チェックによる確認なしでは削除できない。受付確認用秘密値はこのブラウザのsessionStorageに保存し、SNS等に送らない。
- 定期処理：Cloudflare Cron Triggerで毎時実行。失敗した削除は公開・認証停止状態を保って再試行し、失敗が残れば定期処理を失敗として監視対象にする。
- ローカルのみ：`POST /api/platform/dev/retention`で同じ定期処理を試せる。開発者認証の利用可能条件と同一Originを検証し、本番公開ドメインでは拒否する。
- R2：`DELETION_AUDIT`バインディング、非公開バケット`pulbase-deletion-audit`。テストとローカルではエミュレーターを使う。本番バケットの作成・アクセス制限・課金/容量監視は未実施。
- テスト：所有者の違う同名ユーザー、全セッション失効、同意/公開記録の関連削除、特典再取得防止、別Googleアカウント拒否、期限処理、購入保護、再試行、D1の受付を巻き戻した後のR2再削除を検証。
- 実サーバー：専用テストゲストを新規作成し、初回5枚→削除完了→旧セッション401→受付確認まで検証。既存ユーザーは削除していない。
- 最終検証：53ファイル・412テスト成功、型チェック・ビルド成功。実際のDurable Objectで対象プレイヤーの配信停止・観客の接続維持・後続観客への旧状態の非配信も確認。ブラウザでは本人再確認・削除未確認時の無効化・キャンセルを確認。

## 本番復元の手順

1. 公開アクセスを停止する。停止せずにTime Travel復元しない。
2. D1を復元する。独立したR2の削除証跡は復元・巻き戻し・削除しない。
3. 定期処理でR2証跡から削除受付を復元し、対象の全セッション失効と再削除を実行する。
4. 処理成功、処理中受付の有無、削除対象の公開URLが参照不能であることを確認する。失敗があれば公開停止のまま調査する。
5. 復元した利用セッション・再認証・削除確認を全失効し、過去のログイン権限を復活させない。復元時点以後の付与/消費/予約/購入と、DB外の筐体状態を突合する。不一致があれば公開停止を維持する。
6. 確認と運営者の承認後に公開を再開する。2026-10-20に隔離D1/R2・合成データで実Time Travelと再削除・全セッション失効、さらに非公開の専用Workerで実DOの停止/再整合/再開を確認した。既存検証/本番への導入・一般公開切替は別途必要。[復元訓練](recovery-drill.md)と[実DO訓練](do-recovery-drill.md)を参照する。
