# API・WebSocketのサイズ上限と乱用対策

更新：2026-10-16。同一回線の負荷検証に合わせてIPの許容量を調整。検証環境へ実装・反映済み。本番公開の承認や包括的なDDoS対策の完了を意味しない。

## リクエスト本文

| 対象 | 上限・挙動 |
| --- | --- |
| APIの更新リクエスト | 64 KiB。Content-Lengthだけでなく、実際に読んだバイト数で検査 |
| Stripe Webhook | 256 KiB。署名検証用の本文バイト列を保持 |
| 本文の読み込み | 全体で5秒。未完了・読み込み失敗は408 |
| 圧縮本文 | identity以外のContent-Encodingは415 |
| サイズ超過 | 413。業務処理・残高更新に進まない |

UTF-8の日本語や、Content-Lengthなしのストリームも同じバイト上限で検査する。WebhookはブラウザOrigin・頻度制限の例外だが、本文上限と既存の署名検証は省略しない。

## API頻度制限

Cloudflare WorkersのRate Limiting bindingを使い、次の各予算をIP単位と、Cookieがある場合はセッション単位の両方で検査する。どちらかを超えたら429とRetry-After: 60を返す。

| 区分 | 60秒あたりの上限 |
| --- | ---: |
| 一般参照API | 600 |
| 一般更新API | 120 |
| bootstrap | 60 |
| 初回無料クレジット受け取り | 30 |
| WebSocket接続要求 | 120 |
| 認証API | 60 |

IPのキーは環境名とIPから、セッションのキーはCookieからハッシュ化する。生のIPやセッショントークンを制限キー・エラーレスポンスに出さない。ハッシュ化は匿名化を保証するものではない。

local・staging・productionのnamespaceは分離する。検証・本番でbindingが欠ける場合や制限サービスのエラー時は503で業務処理を停止する。ローカルCLIでCF-Connecting-IPがない場合だけネイティブ頻度検査を省略し、本文・筐体・メッセージ上限は維持する。静的アセットと軽量health確認は対象外。

ネイティブ制限はCloudflare拠点ごとの近似的な制限である。この後段に、固定16シャードの共有API予算と全筐体の接続・割当枠を追加した。詳細は[分散アクセス対策](distributed-abuse-protection.md)を参照。共有回線・NATでは複数の正規利用者がIP予算を共有するため、実際の429発生状況を見て調整する。どちらも絶対的な費用上限ではない。[公式仕様](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)

## WebSocket

| 対象 | 上限・超過時 |
| --- | --- |
| プレイヤー・対戦参加者の1メッセージ | 512 KiB、1009で切断 |
| 観戦者・未着席接続の1メッセージ | 16 KiB、1009で切断 |
| 1接続の受信総量 | 1秒に1 MiBまで、1008で切断 |
| 1接続の受信件数 | 1秒に120件まで、1008で切断 |
| ライブフレーム以外の操作 | 10秒に30件まで、1008で切断 |
| バイナリ入力 | 1003で切断 |
| 1筐体の接続数 | 64まで、接続要求に429 |
| 同一IPの1筐体への接続 | 32まで、接続要求に429 |
| 同一検証済みセッションの1筐体への接続 | 4まで、接続要求に429 |

サイズはUTF-8のバイト数で判定し、不正JSONも受信予算を消費する。操作カウンターはattachmentに保持して休止・復帰後も継続する。同時接続要求の競合に備え、非同期処理後・accept直前にも接続上限を再検査する。接続のIPキーはattachmentに置き、ユーザープロフィールとしてD1に保存しない。

制限違反の接続は処理待ちメッセージから再操作できないよう失効させ、退出処理を行う。他の観戦者まで一括切断しない。クライアントの通常再接続は1秒から最大30秒へ段階的に待ち時間を増やし、1003・1008・1009では自動再接続を止める。

途中参加者向けイベント保持は100グループまたは2 MiBまで。上限を超えたら古いイベントだけを間引くのではなく、基準フレームごと破棄して次のキーフレームを待つ。既存観戦者への配送は継続する。

## 公開前に残す課題

- EN-04は対応中。分散アクセスの共有予算・全筐体の接続枠と直近24時間の割当上限は実装済み。大規模な地理分散負荷、入口のDDoS対策、絶対的な支払い上限は別課題。必要に応じてTurnstile・WAF等を追加する。
- Cloudflare予算・R2利用量のメール通知6件、Workers/Pages・D1・DOの利用量監視4通知は設定済み。[利用量監視・検証記録](cloudflare-usage-monitor.md)を参照。メール実着信、429・切断数の継続観測は残る。制限やメール通知を費用上限の代替にしない。
- 実利用規模・共有回線・PC/iPhone/Androidで、通常プレイ・観戦を誤って制限しないか確認する。
- 全メッセージの詳細なスキーマ・権限点検、外部ログの保持・マスキング、結果申告の不正対策はEN-03/EN-05で継続する。
