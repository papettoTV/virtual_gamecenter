# Issue #167: 429復帰テストの待機時間

対象は `read-budget.spec.mjs` の残高更新と、`play-confirmation.spec.mjs` の登録キャンセル後の復帰2件・観戦終了1件。模擬429の待機を60秒から6秒へ変更する。5秒を超える非同期復帰の検査は維持する。

プローブごとにローカル専用IPv6識別子を作り、対象GETの初回と再試行に同じ `CF-Connecting-IP` を渡す。接続先は既存のローカルURL検査で限定する。Cookie、ゲスト、プレイヤー単位の制限、Workerの実レスポンスと残高は維持する。他のGETや書込にはこの上書きを適用しない。実429の場合はWorkerのRetry-Afterをそのまま尊重する。

別途、専用のローカルゲストで実際のbootstrap枠を消費し、実429のRetry-After以上待って1回だけ再試行し、実残高へ復帰するブラウザケースを追加した。このケースの待機時間もUIステップ全体の比較に含める。

対象4件の注入待機は合計216秒短縮する計算だが、新規の実429検査は最大約60秒の待機を追加する。差引約156秒は計算値であり実測値ではない。プレイヤー単位・共有shardの実制限、セットアップ中の実429、実行環境の負荷でも所要時間は変わる。

このsandboxではPlaywrightが未導入のためブラウザ実行・変更前後の計測はできていない。`npm test` はローカルlistenのEPERMで失敗、`npm run build:staging` は成功した。依存・制限の変更は行っていない。

独立CIでは同じ条件のPC・スマホで対象4件それぞれ、新規ケース、UIステップ全体の時間を記録し、実行URLとSHAを上表に追記する。遅い側で2分半〜3分短縮できたか確認し、未達なら実429の待機等の要因を記録する。改善確認前にジョブ分割等の次の施策へ進まない。

同一SHAの初回CI・独立レビュー、develop反映後のWorker専用検証公開、回帰確認、Issueへの実行URL・SHA・計測値の記録は未実施で、マージ後の承認された工程で行う。本変更のローカル検証を公開後の受け入れ完了として扱わない。
