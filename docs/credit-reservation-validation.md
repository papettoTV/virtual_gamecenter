# 全ゲーム共通のクレジット予約検証

更新：2026-10-14。無料ベータでも1プレイのクレジット制をサーバーで維持する。

## 開始手順

1. HTTPで本人のクレジットを仮確保する。
2. HTTPで期限を確認して消費を確定する。
3. 予約IDをゲームSDKからWebSocketへ渡す。
4. Workerが所有者、対象ゲーム/筐体、solo/versus、金額、期限と消費台帳を照合する。
5. D1のcredit_reservation_usesへ一度だけ利用記録を作り、開始応答後にフロントのゲームを開始する。

DOT WAVEだけでなくBUZZ BARRIER・深海サルベージも同じ検証を通る。今後のゲームもカタログの費用を参照する。対戦申し込み・再戦申し込みには本人の有効な未消費予約、対戦Readyには課金者の消費済み予約が必要。再戦ごとに新しいmatch IDと予約を使う。対戦しないゲームへ対戦UIを追加したわけではない。

## 再利用・返却・継続

- 利用記録の予約IDが主キー。並行操作も一度しか認可しない。他人・別ゲーム/筐体/モード・期限切れ・返却済みの予約は使えない。
- 消費は台帳へ一度だけ書く。未開始の消費済み予約は返却できるが、認可済みの予約は返却できない。返却と認可の競合も同じDBの条件付き書き込みで制御する。
- 開始応答を失った場合、使用済みなら「返却しました」と表示しない。開始確認待ちとして通知する。
- 勝者の無料ソロ継続はサーバーが勝敗から発行する一度の権利であり、任意のクライアント要求では得られない。
- 通信切断から2分以内は同じプレイヤーの同じ未終了ソロを復帰できる。明示退出、終了、ログアウト、別プレイヤーによる着席で復帰権を消す。新しいラウンドは別予約が必要。
- 利用記録は予約に従属し、予約削除時にON DELETE CASCADEで削除される。新しい個人情報は保存しない。

## 検証と公開手順

- 全475テスト（Vitest450件、解析11件、公開設定14件）、型検査・検証ビルド成功。
- 検証D1へ0021_credit_reservation_uses.sqlを適用後、Worker f746efb6-09dd-4d83-8043-1b8b5a33068dへ反映。本番DB/Worker/mainは未変更。
- 実develop Pagesの専用ゲストで3ゲームの無払い・他人予約・再利用を拒否。ソロ開始、観戦配送、消費後未開始の返却、開始済み返却の拒否、対戦Readyの課金確認、再戦、勝者継続を確認。
- ゲームSDKの開始応答待ち・予約ID伝達は自動テストで確認。スマホの実操作・全ゲームの見た目はBT-02で別途確認する。
- 本番へ反映する際も追加マイグレーションを先に適用する。旧Workerへ戻すと予約検証が再び不十分になるため、旧版へ単純にロールバックして公開しない。

DBの認可・返却は条件付きSQLとbatchで扱う。[D1 batchの公式仕様](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)を参照。スコアの不正申告対策、負荷/費用制限、障害監視は別の残課題。
