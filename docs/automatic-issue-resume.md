## 再開経路

`実装:自動` に加え、書込権限のある人が `実装:再開` を付けたイベントで1回起動する。
通常の自動ラベルは、従来どおり既存PRがあれば拒否する。
再開時は既存PRがなければ新規実装、あれば同じbot・リポジトリ・Issue・develop向けPRだけを修正する。
複数PR、担当変更、未確定のマージ候補、古いbase、途中のhead変更は拒否する。
既存PRは凍結したマージ候補を起点に修正し、履歴を保持する通常pushだけを許可する。force pushや別PRは行わない。
失敗時の無限再試行は追加しない。修正後も既存の独立レビュー・develop自動マージの判定を通す。

UIケースは `apps/web/tests/ui/*.spec.mjs` に置き、固定fixtureを使用する。
独立CIで使うのは一時D1・ダミー認証・ループバック上のViteだけで、外部HTTP/WebSocketは遮断する。
アプリがローカルURLを5174へ正規化するため、検査も5174を使用する。
PCとスマホ相当のブラウザで結果JSON・画面を保存し、同じCI実行・候補SHA・attemptの成果物をレビューへ渡す。
スマホ実機確認や検証公開後の受け入れ確認が済んだとは扱わず、未確認項目は分けて報告する。
検証公開はdevelopマージ後、人のstaging承認1回、公開・HTTP／ブラウザ回帰1回を維持する。

- staging Environment variable `PULBASE_CONTROL_RULE_VERSIONS` を新しい設定版・strictへ更新

`tools/package-automatic-resume-control.py` はコミット済みHEADから、この3件と既存34ファイルの固定一覧を検査用ZIP／計画JSONにまとめるだけ。
生成器自体はネットワーク・認証・Git書込・bypass変更・公開機能を持たない。
保守が明示的に許可された場合は、確認済みの一時例外のUTC設定版を追加引数に渡し、人用の単独配置ツールも生成できる。
配置ツールはZIPのハッシュ・固定34ファイル・人のstaging承認条件・main更新禁止を照合し、既存3ファイルだけをci-controlへ通常更新する。
確認用manifestは配置しない。残り31ファイルを保持し、発行したContents限定の一時トークンは成功・失敗にかかわらず失効する。
本番検査ポリシーにはレビュー定義のdigestと制御ファイルhashを同期する。
以前の初回追加専用パッケージ作成は通常の本番準備CIから外し、既存の拒否条件テストと公開なしビルド検査は維持する。

現在のci-controlは更新禁止・bypass空のため、人も通常のpushで更新できない。
明示的な保守手順の合意なしに例外追加・ルール解除は行わない。
保護側の配置後は、新しい制御SHA・strict設定版をソースと管理変数へ固定してからdevelopへ反映する。
その後 #80、#79、#81、#82 の順で再開し、古いbaseや承認待ちの多重発生を避ける。
途中で手元担当に切り替えず、#82はPR #83を継続する。
PR #83は旧workflowを含むheadのため、再開前にGitHub画面のUpdate branch等で新しいdevelopへ同期する必要がある。
実装AppにはWorkflows書込権限がないので、権限追加や手元での自動実装ブランチ操作で代用しない。
同期は制御定義を取り込む管理操作に限り、ゲームの修正はActionsの既存PR再開で行う。

本番Worker作成・main反映・本番公開・X投稿は対象外。
