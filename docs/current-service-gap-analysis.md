# サービス要件と現行仕様・実装の差分分析

## 1. 目的

`docs/service-requirements.md` を基準として、2026年8月時点の現行仕様および `prototype-twinkle-psyvaria` の実装を照合し、実現済みの要件、齟齬、未実装、設計判断が必要な事項を整理する。

本書の評価は、次の4段階で表す。

| 評価 | 意味 |
|---|---|
| 実現済み | 要件をおおむね満たす |
| 一部実現 | 基礎はあるが、要件の意図まで満たしていない |
| 未実現 | 仕様または実装がない |
| 要判断 | 要件と現行仕様のどちらを正とするか決定が必要 |

優先度は次の基準とする。

| 優先度 | 意味 |
|---|---|
| P0 | サービスの中心体験、金銭、データ信頼性に直結する |
| P1 | 中心体験を成立させるため、初期公開までに必要 |
| P2 | 成長ループ、運営、拡張性を高めるために必要 |
| P3 | 将来フェーズで対応可能 |

## 2. 総合評価

現行実装は、次の基盤をすでに備えている。

- 一つのゲームを選び、筐体を作成してソロプレイできる
- 筐体固有URLを共有し、別端末からリアルタイム観戦できる
- プレイ中筐体と観戦者数を一覧できる
- 観戦者から対戦を申し込み、対戦・再戦へ進める
- 匿名プレイヤー、Google登録、端末単位のWelcome Creditを扱える
- クレジット仮確保、消費、解除、Stripe購入の基盤がある
- ゲーム結果とランキングを登録・表示できる

一方、サービス要件の中心である「観戦から始まり、人だかりがさらに観客を呼ぶゲームセンター」は、まだ十分に実現されていない。現状は、**観戦可能なゲーム付きプラットフォーム基盤**であり、**ライブプレイを中心に店の熱気が循環するサービス**には至っていない。

特に重要な不足は次のとおりである。

1. 観戦URLからライブへ入るまでに筐体画面と自動クリック処理を経由しており、即時観戦が保証されていない
2. 店舗トップがゲーム一覧中心で、人だかりやライブプレイを主役にしていない
3. 盛り上がりが観戦者数3人以上の赤い点だけで表現され、パルス、密度、広がりを表現していない
4. コメント、リアクション、観客同士の熱気が未実装
5. プレイヤーへ観客増加を控えめに伝える演出が未実装
6. 協力プレイは型定義だけで、状態遷移、通信、UI、ゲーム実装がない
7. ランキング結果をクライアント申告値から登録でき、結果の信頼性が不足している
8. ゲーム、画面、ランキング、APIがBUZZ BARRIERへ強く固定され、選台型プラットフォームへ拡張しにくい

## 4. 現行ドキュメント内の齟齬

### 4.1 規約同意フロー

`prototype-twinkle-psyvaria/docs/platform-experience.md` の基本方針では、トップ閲覧と観戦で規約同意を強制しないと定義している。一方、同文書の「全体体験」図は、サイト訪問直後に規約同意を確認する古いフローのままである。

**対応:** フロー図を現行実装とサービス要件に合わせ、規約同意をユーザー登録・購入の直前へ移す。

### 4.2 匿名プレイヤーの表示名

同文書の「匿名プレイヤー」には「一時的な表示名の使用」とあるが、現行実装は端末に固定された `Player-<ID>` を使用し、変更不可としている。

**対応:** 「匿名プレイヤーごとの固定システム名」へ修正する。

### 4.3 登録必須条件

同文書には「有料クレジット購入時に登録を要求する」とある。実装も購入前に規約同意・登録を促す構成だが、サービス要件では匿名利用の範囲と有料購入条件を明確に一箇所で定義し切れていない。

**対応:** 「有料購入は登録必須」をサービス要件へ明記するか、匿名購入を許すか決定する。

### 4.4 対戦クレジット

サービス要件を現行実装に合わせ、ゲームセンターの乱入に近いルールへ統一した。

- ホストはソロ開始時に消費したクレジットを対戦へ引き継ぐ
- 挑戦者だけが申込み時に1クレジットを仮確保する
- ホストの拒否、時間切れ、開始前不成立では挑戦者へ返却する
- ホスト承認後、対戦起動成功時に挑戦者分を消費確定する
- ホストには、承認すると進行中のソロプレイが終了することを事前に明示する
- 初期仕様の再戦は、負けた側が1クレジットを投入する

**残課題:** 拒否、切断、時間切れ、起動失敗の各経路で仮確保が必ず解除されることをE2Eテストで保証する。

### 4.5 フリープレイ状態

`CabinetState.freePlay` は初期値 `true` のままだが、実装には1クレジット消費が導入されている。

**対応:** `freePlay`を実際の店舗・ゲーム設定から決定するか、不要なら状態から削除する。

## 5. 優先対応案

### 5.1 P0: 中心体験と信頼性

1. 観戦URLからゲーム画面へ直接接続し、DOM文言と自動クリックへの依存をなくす
2. トップを「ゲーム一覧」中心から「今、観客が集まるライブ筐体」中心へ変更する
3. 観戦画面の初期表示に観客の気配と共有導線を追加する
4. ランキング投稿をプレイセッションと結び、クライアント任意値だけで登録できないようにする
5. ソロ開始のcapture条件を、ゲームランタイムからの開始ACKに変更する
6. 対戦申込みの拒否、切断、時間切れ、起動失敗時に、挑戦者の仮確保が必ず解除されるE2Eテストを追加する
7. 観戦、共有、プレイ転換を測る最小限の分析イベントを導入する
8. 有料公開前に法的表示とクレジット法務を確認する

### 5.2 P1: 熱気と安全な初期公開

1. 観客数に応じたパルス・発光表現を店舗トップとプレイヤー画面へ追加する
2. 観戦者向けコメント・リアクションの最小構成を設計する
3. 通報、ミュート、投稿制限、コミュニティガイドラインを用意する
4. 初心者保護の最小ルールを定義する
5. 複数ゲームに向けてゲーム定義、ランキング、筐体生成のハードコードを除去する
6. 観戦・対戦・購入復帰のE2Eテストを追加する
7. 観戦開始時間、状態伝播遅延、エラー率のSLOと計測を導入する

### 5.3 P2以降: 成長とプラットフォーム化

1. 共有経路と関係外への観客拡大を、個人関係を公開せず計測する
2. プレイ終了後の観戦サマリーを追加する
3. 協力プレイを実装する
4. 当日の名勝負・注目ライブを発見する読み取りモデルを作る
5. ゲームマニフェスト、SDK、審査、公開、ロールバックを整備する
6. 運営管理画面とモデレーション機能を整備する
7. リプレイ、複数店舗、権利者ゲーム対応へ進む

## 6. 推奨する次の開発単位

次の開発単位は、機能を個別に足すのではなく、**観戦URLから人だかりへ参加し、そのライブを別の観客へ共有する一連の縦切り**とする。

対象範囲は次のとおり。

1. 共有URLを開く
2. ライブゲーム画面を即時表示する
3. 同時観戦者の気配を表示する
4. 観客数に応じて筐体のパルスが変化する
5. 同じライブURLを共有する
6. 共有経由の観戦開始を計測する
7. 店舗トップの盛り上がり順へ反映する

この縦切りを完成させることで、現在の「観戦できるゲーム」から、サービス要件が目指す「本気のプレイが人を呼ぶゲームセンター」へ最も短く近づける。
