# 監視処理停止・記録陳腐化のコード10通知訓練

## 対象・安全境界

検証専用の `pulbase-service-monitor` を対象とする。通常アプリWorker、Pages、ゲーム、D1の内容、クレジット、Googleログイン、本番は停止・変更しない。負荷試験でもない。

Cron登録を削除すると、そのCronだけでは自動復旧できない。この訓練では既存5分Cronを残し、20分の期限付き設定でscheduledハンドラーの監視処理を全体停止する。停止中はHTTPプローブ・KVの読み書き・D1集計・AEの両スナップショットを一切実行せず、固定名の停止ログだけを出す。期限に達した後の自然Cronは通常処理へ戻る。新しい公開操作口やCron、通知枠、任意時刻・宛先を受け取るAPIは追加しない。

再現するのは「監視の実処理と記録が進まず、最後の正常記録が古くなる」状態。CloudflareのCron配信自体の停止、Cron登録削除の伝播、Cloudflare全体の障害は再現していない。これらと安全な処理停止を混同しない。

## 発見した問題・修正

従来のコード10判定は、最後の死活記録と最後の応答欠落集計の時刻差だった。Cron全体の処理が止まると両方が同時に古くなり、差が増えず10分超の陳腐化を検知できなかった。

応答欠落スナップショットの鮮度を `toUnixTimestamp(NOW())` の実時刻から判定するよう変更した。600秒ちょうどは正常、600秒超はコード10。20分の検索窓に死活記録もなくなった場合は従来通りコード3が優先する。コード1/4/5の優先度、9の閾値、通知先・通知数・Manual/5分評価・5分実行・15分再通知は維持する。通知基盤自体の停止はこのSQLでも検知できず、外部独立監視は残課題。

Cloudflareの[Date and Time関数](https://developers.cloudflare.com/analytics/analytics-engine/sql-reference/date-time-functions/)と、実SQL APIの読み取り専用31ケースで構文・境界・優先順位を確認する。合成SQL評価は通知や記録を作らず、実メールの代わりにはしない。

## 実施・復元

`apps/web` で実行する。監視Workerの他の変更・訓練と並行しない。

1. 全テスト・型検査・stagingビルド・監視Worker dry-runを確認する。
2. 既存ポリシーの陳腐化判定だけを修正し、保存後の再表示でSQL、宛先、間隔、閾値を照合する。
3. `node scripts/start-slo-drill.mjs --environment staging status` で集計正常・最新値0を確認する。
4. `node scripts/start-slo-drill.mjs --environment staging pause` を一度だけ実行する。固定のstagingリソースと通常DB、最新の死活正常・集計正常・通知0を検証する。不正設定・既存障害では開始しない。開始試行・期限を管理外の `.wrangler/monitor-cron-pause.json` に記録し、同じ作業場所からの24時間以内の再開始を拒否する。これは分散ロックではない。
5. 自然Cron予定を複数回またいでも実記録の時刻が進まず、最後の記録から600秒超で通知SQLが10になること、検証サイトが正常なことを確認する。時刻・記録・閾値を人工的に操作しない。
6. 同一ポリシーのAlertメール本文のTrigger 10、評価時刻とメール日時を照合する。以前のコード10メールやテストメールを代用しない。
7. 確認後すぐ `node scripts/start-slo-drill.mjs --environment staging restore` で基準設定へ戻す。statusや解析トークンに障害があっても復元を先に実行できる。一時変数が消えたこと、自然Cronの死活・D1集計が新しい通常記録で再開したことを確認する。
8. 通知0と同じポリシーのResolvedメールを照合する。データが0件であることをゲーム成功や月間SLO達成の証明にしない。過去の故障記録を消さない。

期限前の復元に失敗した場合も、期限後の自然Cronで処理再開するが、最終的に基準設定の再デプロイで一時変数を除く。期限自体はCron配信を復旧させるものではない。20分を超えてコード3が出た場合は10と区別し、実際の未記録期間・復元状態を調べ、通知を黙らせるため閾値を変えない。
