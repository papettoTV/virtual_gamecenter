# CI照合の待機時間と診断分類の修正

## 観測した停止

PR #141（head `a8e35747ecebc4706cea716aa941534d4110c274`）の通常CI
`42308624242`は単体・PC・スマホ・verifyまで成功した。一方、独立レビューの前提となる
Candidate tests `42308624210/job/128204383513`は10分の照合待機で停止した。
照合停止は2026-11-06 23:09:17 UTC、通常CIのverify完了は23:09:23 UTCだった。
失敗したUIケースはなく、reviewは前提不合格で実行されていない。

通常CIはUIジョブ15分＋verifyジョブ5分を許容するが、従来の照合は10秒間隔60回だけだった。
さらに診断処理はCandidate testsを収集せず、アプリ診断が空になったため
`diagnostic-unavailable`で停止した。これはアプリ修正を追加実行する理由ではない。

## 変更

- 照合の既定期限を25分（UI15分＋verify5分＋待ち行列/API反映の余裕5分）とし、
  API読取にかかった時間も含めて有限の期限で終了する。Candidate testsのジョブ上限は
  自身の準備時間を含め30分とする。長時間の待ち行列や障害でも無限には待たない。
- CIの成否・対象SHA・候補SHA・必須job・成果物条件は維持する。失敗した最新CIを
  古い成功へ置き換えず、初回実行を求める後段の信頼条件も変更しない。
- CLIは秘密情報を含まない固定コードだけを`CI_EVIDENCE_RESULT`へ出力する。
  期限切れ・API読取失敗・CI不適格・成果物不適格・対象変更を区別する。
- 診断処理は失敗したCandidate testsも読み、`ci-control`として分類する。
  旧runに分類コードがない場合は原因を推測せず、候補照合の失敗として記録する。
  ログそのものや未認証の任意メッセージを実装エージェントへ転送しない。
- developとの同期が不要でCI照合だけが不合格の場合、アプリ実装モデルを消費しない。
  最新developの同期が必要な場合と、アプリの具体的なUI/単体/レビュー不合格もある場合は、
  既存の有限同期・修正経路を維持する。

## 検証と反映順

14分後にCIが成功するケース、API時間込みの期限切れ、最新CI不合格、API障害、旧ログ、
診断の機密情報非転送、通知重複拒否、アプリ修正を起動しない分岐を自動検査する。

信頼定義の変更には、人が管理する一括配置ツールを使う。ci-controlの変更は信頼定義3件
だけで、残り31件・公開処理は保持する。ツールが人の管理端末で一時bypass・配置・
bypass削除・strict再検査・2変数の更新と確認まで行う。AIへ管理用の鍵を渡さない。
配置後の新しい制御SHAをdevelop側の固定参照へ反映してから、この設定PRを取り込む。

その後、既存PR #141へ最新developを同期し、新しいコミットの初回CI・独立レビュー・
自動マージを確認する。既に失敗したrunのattempt 2で信頼条件を満たそうとしない。
アプリの追加実装修正枠をこの変更で増やさない。

staging公開は実マージ後の初回CI成功と人の承認1回を必須とし、strict・通常運用のbypass空、
main・本番・SNSに反映しない条件を維持する。公開後の個別受け入れは別途確認し、
設定PRの成功だけでIssue #132/#134の全体完了とは扱わない。
