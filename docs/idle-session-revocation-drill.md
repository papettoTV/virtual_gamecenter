# アイドル接続失効・RPC障害通知の総合訓練

対象はdevelop / 検証Workerと、別リソースの非公開訓練Worker。負荷試験・本番変更ではない。

## 実装

- 認証済みWebSocketが存在する筐体では、DOのalarmで約60秒間隔にD1のセッションを再確認する。クライアントの送信・ping・通常の失効RPCの成功に依存しない。
- 同じセッションはまとめ、筐体の最大64接続を1つのIN検索で検査する。削除、期限切れ、退会要求済み、旧形式の不完全な資格情報は1008で切断する。DB検査失敗時も認証済み接続をfail-closedで切断し、匿名観戦は残す。
- 先にrevokedを記録し、退出処理・接続枠の返却を行う。有効な別セッションは維持する。alarmはゲームの状態保存で先送りしない。匿名観戦だけなら高速な再検査を続けず、従来の日次整理へ戻す。
- 途中の障害でrevoked印だけが残り、まだOPENの接続も次のalarmで再切断・枠返却する。旧形式でsession hashが欠けている接続も切断する。この2ケースは実WebSocketを使うローカル回帰テストで確認する。
- 同じDOのalarmを日次整理と共有する。既存の早い予定は維持し、alarm終了時にも次を予約する。setIntervalでDOを起動し続ける方式ではない。Cloudflareのスケジューリング遅延・障害を含む60秒の厳密な上限保証ではない。
- `idle-revocation-v1` は切断または検査/後処理失敗時だけ匿名集計する。通常の正常検査を毎分記録しない。新しいCronや外部APIトークンは不要。1分あたりD1照会1回/認証接続のある筐体とDO alarmの費用・無料枠消費は発生し得るため、既存利用量通知で監視する。

## 既存接続への起動

新規接続とDOの再起動時にalarmを設定する。ただし、新版デプロイだけで全休止DOが直ちに起きるわけではない。リリース時には一度、次を実行する。

```sh
cd apps/web
node scripts/activate-session-sweeps.mjs --environment staging
```

Cloudflare認証済みCLIから非公開の`SessionMaintenance` Service Bindingを呼び、D1の筐体対応表を50件ずつ、最大10ページまで処理する。HTTP管理APIは追加しない。失敗したページを成功として進めず、再実行も予定を先送りしない。本番・対象の上書きは拒否する。500件以上ある場合は上限を黙って解除せず、別途計画を見直す。

今回、既存の6筐体への起動が成功した。これは全利用者の一括ログアウトではなく、各DOの独立した失効確認の起動。

## 実障害の隔離範囲

`apps/web/config/revocation-drill.json` の専用Worker `pulbase-revocation-drill-20261020`、専用D1 `9787b59a-a5cb-46f2-b10d-26a0ab679493`、専用DO名前空間を使用する。workers.dev・preview URL・routes・Cronは無効。通常の検証/本番DB、R2、Google/Stripe Secretは接続しない。

実際に配備したDOの失効RPCを故障スイッチで例外にする。単にAnalytics Engineへ偽の障害点を直接書く訓練や、Cloudflare全体の実障害を起こす訓練ではない。失効対象は合成Google連携レコードのテスト利用者だけで、本物のGoogle通信は行わない。故障スイッチは最長10分で失効する。

正常経路と同じログアウト処理から警告を記録し、既存の検証集約通知を自然発報させる。通知評価に含めるためblob1はstagingのまま、blob4に`revocation-drill-v1`を付けて訓練分を識別する。通常サービスの死活記録とコード0〜5、既存の費用・利用量通知は維持する。Testボタンによるメール送信は今回行っていない。

## 手順と確認

1. 専用設定を`validateRevocationDrill`で検査し、専用D1だけに移行を適用。dry-run後、非公開訓練Workerを配備する。
2. `node scripts/revocation-drill.mjs config/revocation-drill.json exercise` を実行。loopback8798からprivate Service Binding経由で3ゲームを順番に検証する。
3. 各ゲームで失効対象、有効な別セッション、匿名観戦者の3接続を用意。RPC故障中にログアウトし、HTTP 200/D1失効後も旧接続が残ることを確認する。
4. 旧接続からアプリメッセージを送らず、実alarmで1008切断。有効な別セッションと匿名観戦が応答を続けることを確認する。
5. 故障を解除し、新セッションのログアウトが実RPCで認可対象1→0、クライアント1008切断になることを確認。各ケースで接続枠0を確認する。
6. `node scripts/revocation-drill.mjs config/revocation-drill.json quiesce` で、訓練用の全筐体・監視alarmを停止し、接続枠0を確認する。通常検証/本番の全体停止ではない。
7. メールのTriggerが4以上になる自然発報を確認。最後の障害から20分以上再発なし、集約条件0、旧接続切断と正常RPCを合わせて復旧判定する。無警告だけでは復旧としない。コード2は従来の死活復旧でありRPC復旧とは区別する。

RPC返却オブジェクトはDTOとしてコピー後に`Symbol.dispose`で解放する。終了処理のRPC thenableは`.catch`を直接チェーンせず`try/await/catch`で処理する。準備中に見つかった合成名の一意制約・筐体UUID形式・返却値/終了処理の問題は訓練ツール側で修正した。初期失敗を製品の成功ケースとして数えない。

## 制約

- 同じDOのplatform alarm自体が動かない障害や、全Cloudflare拠点の同時停止を再現したものではない。
- アカウント監視の値には他作業の利用量も含まれる。少数接続の機能訓練を長時間・高負荷試験の代わりにしない。負荷試験は保留・未合格。
- DB復元、一斉停止の本番導入、実ユーザーを対象にした再失効は実施しない。
- 訓練DB/DOは合成データのみで停止状態として保持。再試験は新しい筐体を作る。不要になったら、名前とIDを照合して専用リソースを別途整理する。
