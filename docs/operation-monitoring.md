# ゲーム開始・ログイン・無料付与の処理結果監視

更新: 2026-10-20。検証環境のみ。本番・main・負荷試験は対象外。

## 測定する境界

HTTP 200や消費の確定だけを「ゲーム開始成功」とは数えない。既存処理の結果を共通ヘルパーで測り、残高や状態遷移、権限検証のロジックは変更しない。

| 操作 | 成功を記録する位置 | 分母から除くもの・制約 |
| --- | --- | --- |
| solo_start | DOがクレジットを検証し、状態の保存と開始許可を送信した後 | 不正/再利用予約、失効中の操作はrejected。再開許可も含む処理回数であり、ユニークプレイ数ではない |
| versus_start | 両者の準備後、カウントダウン送信・状態保存が完了した後 | 片方だけ準備済み、無関係なメッセージはnoopで記録しない。参加条件不成立はrejected |
| google_login | 有効なセッション・同意・stateを確認したGoogle callbackの完了後 | 利用者のaccess_deniedはcancelled、アカウント不一致等はrejected。不正stateは記録しない。再認証も含む |
| welcome_credit | 初回特典のトランザクションで台帳への追加が完了 | 既に付与済み・並行要求の追加なしはnoop |
| registration_credit | 新規登録のトランザクションで登録特典が追加された後 | ログインだけ、保持済み特典との照合で追加なしは記録しない |
| daily_credit | 日次補充のSQL結果が実際に正の補充額を返した後 | 残高十分、未資格、補充済みはnoop。補充判定SQLの障害もfailureだが、全件を付与漏れと断定しない |

予期しない例外はfailureとして記録し、元の例外をそのまま再送出する。Googleの設定不足・有効stateでのプロバイダー障害もfailure。計測の書き込み自体が失敗しても本処理を失敗にせず、固定ログ`operation_metrics_failed`だけを出す。

`APP_ENV=staging`で既存`SECURITY_EVENTS`を利用する。本番/localでは送信しない。将来の本番導入は環境分離・通知とともに別途確認する。

## 個人情報と件数

- 既存の`pulbase_service_health`にschema `operation-v1`で送信する。新しいDB・dataset・Cookie・Cron・Secretは追加しない。
- 記録は環境、固定の操作名/結果、ゲームカタログのID、固定の集計キー、件数のみ。URL、OAuth code/state、IP、筐体ID、プレイヤーID/名前、メール、セッション/予約ID、例外本文は送らない。
- blobsは環境/操作/schema/結果/ゲーム/集計キー。blob6は`operation-start-v1`、`operation-login-v1`、`operation-credit-v1`。doubles1〜5は技術判定の分母/技術失敗/成功/拒否/キャンセル。
- failure rateは`failure / (success + failure)`。rejected/cancelledは別に数える。対象なしの率は0ではなくnullと`no_eligible_data`を返す。
- noopは送信しないため、残高確認のポーリングを成功回数として水増ししない。各操作の結果につき最大1点。Google新規登録が特典付与も行う場合、別の2操作として各1点になる。
- 既存方式同様、SQLではsampleIntervalを考慮した推計件数を使う。厳密な台帳件数や課金の根拠にはしない。AEの取り込み遅延・サンプリング・送信欠落があり得る。

## 20分集計と通知

`apps/web/scripts/operation-report.mjs --environment staging`は、管理外の`.dev.vars`の既存`CLOUDFLARE_METRICS_TOKEN`で読み取り専用の集計を行う。対象アカウント・環境・dataset・20分窓を固定し、任意URL/SQLの指定は受け付けない。結果の上限に達した場合は切り捨てた結果を正常とせず失敗させる。

既存通知`0677e7f471c44e79adf07c6bacc40b37`へ、各分類が**直近20分で技術失敗3件以上、かつ失敗率20%以上**の場合のコードを追加した。初期の無料ベータで、単発失敗や利用者キャンセルによる過剰通知を避けるための暫定値。98%の開始成功率目標と同じ閾値ではない。

| コード | 分類 | 対応 |
| --- | --- | --- |
| 6 START | solo_start / versus_start | 開始処理、DO/D1/保存・クレジット検証の例外を調べる。残高不足を障害に含めない |
| 7 LOGIN | google_login | Google応答・設定・登録/再認証の例外を調べる。拒否・キャンセルを障害に含めない |
| 8 CREDIT | 初回・登録・日次の無料付与 | 台帳/特典処理を調べる。手動加算や再付与で帳尻を合わせず、重複とトランザクション完了を確認 |

優先度は3 NO DATA > 1 DOWN > 4 REVOKE > 5 RETRIES > 6 START > 7 LOGIN > 8 CREDIT > 2 RECOVERED。複数同時障害では先頭の1分類のみメールに出るため、必ず全分類の集計を確認する。

閾値1以上・Manual・5分評価/実行・15分再通知、宛先は既存登録メールを維持。費用/R2の6通知と利用量4通知もEnabledを確認し、新しい通知枠は作っていない。件名の凡例に6/7/8を追加した。0は「発報条件なし」であり、操作成功や回復の証明ではない。2は従来どおりサービス死活の復旧だけを表し、6/7/8の個別復旧通知ではない。

初回の複合条件SQLは通知画面のプレビューで422になったため、固定集計キーで条件を簡略化。SQL APIと通知プレビューの両方を再検証した。保存後、通知一覧のEnabled・再表示したSQL全文と名前の一致・Manual/5分/15分を確認した。

## 運営者専用画面

検証環境の `/operator/operations` で、直近20分の開始・Googleログイン・無料付与について、判定対象件数、成功、技術失敗、失敗率、拒否、キャンセル、通知判定を表で確認できる。「集計を更新」で手動再取得する。自動ポーリングは行わない。対象なしは「—（対象なし）」、取得障害は503のエラー画面とし、0件・正常・古い集計で代用しない。

- Googleログイン済みで、検証WorkerのSecret `OPERATOR_ACCOUNT_IDS`（カンマ区切りの許可アカウントID）に含まれる利用者だけが閲覧できる。ゲスト・一般登録者・失効/期限切れ/退会中セッションは拒否する。画面を開くだけでセッションの期限を延長しない。
- 初期許可は運営者が指定したGoogleメールを検証DBで照合し、変更されにくい内部アカウントIDへ解決して設定する。メール・ID・APIトークンはGitやHTMLに埋め込まない。追加・削除はSecretの更新で行い、削除後は次のアクセスから拒否する。
- 既存のサイトBasic認証だけでは運営権限を与えない。許可設定がない場合も公開しない。本番・localでは404。認証・DB障害時は拒否側に倒す。
- `/api/operator/operations` は同じ権限検査を行う読み取り専用JSON。任意SQL・対象環境・集計期間は指定できない。画面もAPIもGETのみ、クエリ指定とcross-siteのサブリソース取得を拒否する。外部リンクからの画面へのトップレベル遷移は、通常の権限検査のうえ許可する。
- 既存APIのIP/セッション別レート制限を画面にも適用。秘密のMetricsトークンはWorkerから固定のCloudflare SQL APIへだけ送る。応答は64KiB、タイムアウト10秒、集計行数64未満に制限する。
- CLIと画面の20分SQL・集計式は `src/shared/operation-report.mjs` を共有する。取り込み遅延・推計件数・サーバー側の測定境界・通知閾値・対象なしの意味を画面にも表示する。初版には月間集計がなく、下記の2026-10-21追加もSLOの正式な達成判定ではない。
- `private, no-store`、noindex、CSPでフレーム埋め込み・スクリプトを禁止。外部の解析・画像・フォントを読み込まない。

## 月間参考集計（2026-10-21）

同じ運営者専用画面とJSON APIに、今月のサーバー処理の参考集計を追加した。月初は日本時間の1日0時、終端は取得時刻の5分前（未満）。月が変わった直後の5分間は始端と終端を同じにし、前月分を混ぜない。UTCの対象期間も表示する。任意の月・期間・SQLを利用者から指定させず、従来のstaging限定・Google連携/許可アカウント・失効検査・キャッシュ禁止を維持する。

- 成功率 = 成功 /（成功 + 技術失敗）。拒否・キャンセルを分母から除く。開始は運営手順の98%を参考目標として差をパーセントポイントで表示。ログイン・無料付与に未決の目標を勝手に設けず「未設定」とする。
- 対象なしは率・差ともnull。目標以上でも「目標水準以上（参考）」であり「達成」や「正常」にはしない。月途中・計測開始前・欠測・サンプリング、開始前の失敗/受信できなかった許可の未捕捉があるため、月間SLOを満たした根拠には使わない。
- 月間SQLだけで `blob7 = 'operation-drill-v1'` の隔離通知訓練を除外。通常の検証用疎通は区別できないため含むと明記する。既存20分集計・メール通知条件・通知枠は変更しない。
- 手動更新1回につき固定SQLを従来の20分と月間で計2回実行。月間は最長31日、各64行未満・64KiB・10秒の制限を維持。どちらかが失敗したら503で、旧値・20分値・ゼロを月間値の代わりにしない。自動ポーリングは追加しない。新しいイベント、DB/移行、Cookie、Cron、Secret、データ保存先は追加しない。
- この環境のSQL APIでは期間条件内の `toDateTime()` は422となった。実APIが要求したUTCタイムゾーン付きISO 8601リテラルで照合し、日本時間の月境界・年越し・うるう年・取り込み余裕・権限・欠測時の動作をテストした。日時はサーバーのDateからのみ生成する。

## 残課題（継続）

- 6/7/8の自然条件発報・実着信・回復は[隔離訓練](operation-notification-drill.md)で確認済み。開始・初回付与の実D1エラーと有効stateのGoogle障害応答を各3件実行し、通知条件を変えずに実メールとResolvedを受信。実Google再認証も成功した。本番や一般利用を止めたものではない。
- 複数分類の同時障害では、メールが優先コード1件だけになる。今回の順次訓練を、分類ごとの独立した同時障害・個別回復監視が完成したものとは扱わない。
- WSメッセージがサーバーへ届く前の切断、DOの起動前/権限確認前の失敗、クライアントが開始許可を受信できなかった場合は、この分母で完全には捕捉しない。
- Google callbackのセッション/state/同意確認より前のDB障害はログイン分母の対象外。登録付与の事前照会の障害も付与トランザクション失敗とは別。無料付与成功と応答後の表示成功も異なる。
- ingressから開始/タイムアウトまでの整合、欠落補正を含む月間SLOの正式判定、通知パイプライン自身の欠落検知、分類別・ゲーム別の回復監視、本番/別事業者の監視は残す。今月の参考集計を追加しただけでこれらを完了にはしない。
- 監視対象なしを正常と断定しない。公開判定・本番反映・長時間負荷試験は引き続き別課題。
