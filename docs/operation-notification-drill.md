# 開始・Googleログイン・無料付与の通知・復旧訓練

対象は検証環境。長時間負荷試験・本番・mainの公開判定とは分離する。

## 安全な構成

- 既存の非公開Worker `pulbase-revocation-drill-20261020` と専用D1 `9787b59a-a5cb-46f2-b10d-26a0ab679493` を再利用する。通常の検証DB・本番DBは接続しない。public route / workers.dev / preview URL / Cron / Google・StripeのSecretはない。
- `config/operation-drill.json` で訓練用entrypointを選択する。元の失効訓練用RPC・DO class名・migration・既存データは維持。今回のHTTP entrypointは常に404で、元のWebSocket経由の失効訓練を再実施する場合は元のconfigで再デプロイする。追加した `OperationOperator` はローカルのWranglerから一時Service BindingのRPCでのみ呼び出す。
- CLIはWorker名・アカウント・専用DB ID・環境・禁止bindingを検証する。RPCは2つの訓練フラグ・staging・想定外の登録identityがないことを検証する。旧訓練の未登録合成ゲストは残っているが、操作対象は新規に生成した合成プレイヤーと筐体だけ。
- 各分類・各モードをUTC日付で1日1回までに制限。失敗は3操作、正常復旧確認は13操作が上限。実行記録は専用DBの `operation_drill_executions` に残す。途中失敗でも自動再実行しない。先に記録・部分実行結果を確認し、無条件に記録を消してやり直さない。
- クレジット・ゲームの本処理から生成された `operation-v1` を既存datasetへ転送し、`operation-drill-v1` の固定タグを付ける。故障値・時刻・メールを直接作ったり、通知閾値を下げたり、テスト送信ボタンで代用したりしない。通知中は検証の運営者集計にも合成処理が含まれる。実績・課金・SLOとして利用しない。

## 障害と復旧の境界

| 分類 | 隔離環境で実行する障害 | 復旧確認 | 訓練しない範囲 |
| --- | --- | --- | --- |
| START / 6 | 実DOのsolo開始・クレジット使用記録に限り、不成立SQLによるD1エラーを起こす | 注入なしで13回の予約・消費・開始許可が完了。各筐体を停止・接続終了する | 一般利用者の開始停止、全ゲーム/対戦の同時障害、負荷・性能測定 |
| LOGIN / 7 | 合成セッション・正しいstate・同意を持つcallbackへ、プロバイダーのtemporarily_unavailable応答を渡す | 通常の検証サイトで実Google再認証を確認し、失敗イベントの20分窓離脱後に解除を確認する | Googleそのものの停止、Googleへの異常通信、新規ユーザーの実登録、セッション/state以前の障害 |
| CREDIT / 8 | 初回無料付与のトランザクションだけを、不成立SQLで失敗させる | 原処理で13人の合成ゲストへ付与成功。失敗時台帳0件・成功時1件を照合 | 実ユーザーへの手動加算、購入・Stripe、登録/日次付与の実障害（別途単体試験） |

開始のSQL注入はDO内の当該呼び出しだけで有効。最大60秒の期限を持ち、finallyでも解除する。HTTPで注入を有効にする経路はない。無料付与の不成立SQLも1回の関数呼び出しに閉じる。

## 実施順

1. 通常7項目・死活Cron・現在の通知値と3分類の集計を確認。別の実障害や上位優先通知がある場合は訓練しない。
2. `apps/web` で `node scripts/operation-drill.mjs start-fail` を実行。既存SQLの値6・メール本文のTrigger 6・開始時刻・受信時刻を照合する。
3. `start-recover` を実行。非加重の3失敗/16処理は18.75%だが、SQLはサンプリングを補正した推計値なので実際の判定も確認する。実正常処理、通知SQL 0と同じポリシーのResolvedメールを確認。解除されなければ、閾値を下げたり成功を追加注入したりせず20分窓離脱を待つ。失敗記録は消さない。通知解除は「失敗0件」を意味しない。
4. `login-fail` で値7・実メールを確認する。隔離callbackとは別に検証サイトの通常Google再認証を行う。実アカウントを退会/再登録/消費しない。失敗記録が20分窓から外れるまで待ち、成功処理と通知値0・Resolvedメールを確認する。無操作・対象なしだけを復旧証明にしない。
5. `credit-fail` → 値8・実メール → `credit-recover` → 正常付与・台帳照合・通知値0・Resolvedメールを確認する。
6. `quiesce` を実行。訓練筐体の停止、接続枠0と保守アラーム停止を確認。故障の持続・呼び出し用proxy・定期訓練を残さない。DBの合成記録は保持し、削除したとは扱わない。

読み取り用の集計は `operation-report.mjs --environment staging`、または[運営者画面](https://develop.virtual-gamecenter.pages.dev/operator/operations)。メールは受信済みの実メッセージを確認する。Alert started（評価時刻）とメールの受信時刻は異なる。遅延した繰り返しメール・以前の訓練メールを今回のものと誤認しない。

費用/R2の6通知・利用量4通知・サービス監視1通知の枠と宛先、SQL、5分評価/実行・15分再通知は維持する。CloudflareのResolved通知はSQLが閾値未満に戻ったことを示す。コード2の死活RECOVEREDや、アプリ全機能の復旧と混同しない。

### DOT WAVE統合テストの実行分離（2026-10-21）

上記は2026-10-20時点の記録。同じテストコードの次のCI `39415875007` は成功しており、特定のゲーム操作が必ず停止する問題ではなく、実行条件に依存するタイムアウトだった。失敗時はメッセージ待機の3秒エラーではなく、テスト全体の5秒制限に達していた。他ファイルとの並列実行によるリソース競合を有力要因として、タイムアウトの延長や自動リトライではなく、実行プロセスを分離した。特定のRPCやDB処理が原因だと断定できるログはない。

- `vitest.dot-wave.config.ts` に17件を移し、通常の並列スイートから除外。`npm test` は通常スイート終了後に `npm run test:dot-wave` を必ず実行する。テストの削除・スキップ、ゲーム/Workerの動作変更はない。
- テスト全体5秒・各メッセージ待機3秒は変更しない。CIでは全テストに加えて独立プロセスで17件を3回連続実行し、どの回でも失敗すればジョブを失敗させる。成功まで繰り返すリトライではない。
- 公開対象の全767件、ローカル反復51件、型検査・staging向けビルドが成功。反復の対象ファイル実行時間は約1.7〜2.1秒。未公開の別作業を含む元の開発ツリー816件も成功したが、公開対象の件数とは区別する。
- [CI 39494704933](https://github.com/papettoTV/virtual_gamecenter/actions/runs/39494704933)（`d6992b0`）は全767件・追加反復51件・型検査・staging向けビルドまで再実行なしで成功。CIで対象ファイルの実行時間は通常実行3.05秒、追加3回は2.89/2.87/2.98秒で、17件すべて成功した。今後もこの反復をCIに残して再発を検出する。
- 本番・main・通常検証Worker・DB・Secretを変更せず、リモート負荷試験は行っていない。Gitのpushに伴うPages検証プレビューの自動ビルドと、バックエンドのデプロイは区別する。長時間負荷試験は引き続き保留・未合格。
