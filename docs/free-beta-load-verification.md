# 無料ベータの負荷検証

更新：2026-10-16。検証先は develop.virtual-gamecenter.pages.dev のみ。本番・main・有料プランは変更しない。

## 初期の検証基準

運営者から同時利用数の数値指定がないため、初回の工学的基準を以下とした。公開後の需要予測や収容人数の保証ではない。

- 実環境：24接続、6筐体（3ゲーム各2筐体）、プレイヤー6人・観戦18人。同一の外向きIPから接続。
- 集中観戦：24接続、1筐体、プレイヤー1人・観戦23人。同じIPから接続。
- 各ケース120秒。約20Hzを目標に1KiBの動作フレーム、約1秒ごとに8KiBの基準フレームを配送。5秒ごとのclockPingと、24人が3ゲームの一覧を10秒ごとに読む負荷を重ねる。
- 全員が通常のbootstrapで識別Cookieを取得し、プレイヤーだけ通常の無料特典・予約・消費・開始を経る。認証済み利用者のDB照合も省略しない。
- 短時間の枠回復確認：3筐体に同一IPで64接続し、65接続目を拒否。全切断後に再接続できることを確認する。
- 単体回帰：複数回線96人の枠確保、同一回線24人の到着・一覧更新、個人制限維持、IP/全体上限超過の拒否、切断・退会時の返却。
- 合格基準：意図しない429/503・切断・アプリケーションエラー0、最終フレーム到達、動作フレーム99%以上配送、配送/clock往復p95が1秒未満。配送時間は同じ計測PCの送受信時計で測る。クライアントの描画時間ではない。
- 配送件数は単調増加するseqだけを数える。後着の古いフレームは採用しないため、この率をTCPのパケット損失率と解釈しない。

## 検出した問題と対処

1. 修正前の実Pagesで6筐体へ24観戦接続を作ると、16成功・8拒否。同一回線の全筐体16接続上限が正規利用を制限した。
2. 1筐体のIP8接続上限も集中観戦24人には不足。筐体内IP32・全筐体IP64へ拡大。全体256・利用者8・セッションの同一筐体4・24時間200筐体は維持。
3. IPと個人が同じ予算だったため、複数人の到着や一覧更新を1人分の枠で処理していた。IP予算を個人予算と分離。検証済み個人の予算は緩めない。共有シャード予算・Native Rate Limitingも残す。
4. 3ゲームを3秒間隔で更新すると、24人で毎分1,440要求。10秒間隔で432要求へ70%削減し、非表示タブでは停止。復帰時に更新する。更新操作・共有枠自体を無効化していない。
5. 24人が1時間一覧を閲覧する計算では25,920要求。IP/共有シャードの日次参照30,000までの範囲を回帰テストで確認。個人ごとは1,080要求で日次2,000内。この計算は1時間の実時間soak試験の代替ではない。
6. 3ゲーム共通の一覧鮮度テストで、BUZZ BARRIERだけ開始20秒後に一覧から消える既存処理を再現した。他2ゲームだけが基準フレーム受信時に一覧を更新していたため、全ゲームで5秒以上経過したら更新するよう修正。実環境の一覧ポーリングも、作成した全筐体が残ることを検査する。

## 実行証跡

- 修正前の接続測定：6筐体24人中16成功・8拒否。
- IP予算・更新頻度修正後の120秒測定：6筐体24人は全接続成功、37,818動作フレームの期待配送に対し37,809受信（99.976%）、配送p95 407ms、clock往復p95 525ms、一覧792要求。意図しない切断・アプリケーションエラー0。
- 同じ120秒測定の集中ケース：1筐体24人は全接続成功、49,289/49,289配送（100%）、配送p95 284ms、clock往復p95 385ms、一覧792要求。切断・アプリケーションエラー0。
- 120秒測定の実フレーム頻度は約17.5〜17.9Hz。目標20Hzとの差には、負荷生成側で一覧要求を待つ時間も含む。サーバーの最大配送性能と解釈しない。
- 一覧の鮮度修正後の最終Workerは `ed14495c-7ea1-4b42-9212-3055a6a3208f`。全535テスト（Vitest 501、アクセス解析11、公開設定17、監視6）・型検査・検証ビルド成功。

## 再実行

`apps/web`で `npm run test:load -- --confirm-staging` を実行する。Node 22とlockfileの依存が必要。

- 認証情報は `PULBASE_LOAD_AUTH_FILE` で指定するローカルJSON（username/password）。既定は `/tmp/pulbase-staging-access.json`。Gitへ登録しない。
- URLは検証Pagesに固定。本番URL指定、ヘッダーによる送信元IP偽装、残高の直接書き換え、検証専用サーバーAPIは用意しない。
- `LOAD_DURATION_SECONDS` は30〜300秒、既定120秒。ストリーム負荷は最大24接続、最後の短時間の枠検査だけ64接続。ケース間は65秒待機する。
- `--capacity-only` はストリーム負荷を省略して枠検査だけを行う。前の実行から65秒以上空ける。
- `--probe` ではクレジットを取得せず観戦の接続可否だけを測定する。probeのsuccessは測定完了を示すだけで、全接続の成功を意味しない。
- `LOAD_REPORT_PATH` に集計JSONを出す。既定 `/tmp/pulbase-beta-load.json`。Cookie・認証値・プレイヤー名は出力しない。
- 一覧取得は負荷を保守的に重ねる。プレイ中の画面で実際に24人全員が一覧を開いていることを意味しない。
- 正常終了・検査失敗時は全接続を閉じる。強制終了時はTCP切断とサーバー側照合で回収する。再実行を連発せず、枠回復と予算の残りに注意する。作成したテスト用ゲストと台帳は通常の保存・削除方針に従う。

## 確認範囲と残課題

- これは合成クライアントによる開始・観戦配送・DB/API・接続枠の検証。ブラウザでゲームAIや物理演算を実行するベンチマークではなく、PC/iPhone/Androidの描画FPS・タッチ操作・通信断復帰は別途確認する。
- 96人はWorkersテスト環境の枠検査であり、実インターネット上の96接続検証ではない。多数の地域・回線からの分散負荷は未実施。
- 数時間〜日次の連続soak、最大512KiBメッセージの集中、回線帯域制限・大きなパケットロス、256接続限界の実環境試験は未実施。
- IP予算を広げた分、共有シャードの日次受付余地も増える。無料枠内の利用や絶対的な支払い上限を保証しない。費用・利用量監視を維持し、429と実際の正規利用を見て調整する。
