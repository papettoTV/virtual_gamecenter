# 無料ベータのクレジット消費・返却ルール

更新: 2026-10-22。対象はソロプレイと観戦。Issue #28、#31。購入再開・対戦公開・切断復帰対策の追加統合は行わない。

## 利用者向けの基準

観戦と開始確認画面の表示は無料。現在の3ゲームは、新しいプレイごとに1枚を消費する。終了後のリトライも別の1プレイとして1枚必要。初回5枚・登録5枚・日次補充の条件は変更しない。

| 状況 | 消費・返却 | 注意点 |
| --- | --- | --- |
| 開始確認をキャンセル | 消費なし | ゲームのREADYと、消費前の開始確認画面は別 |
| 仮確保だけ済み、消費確定前にキャンセル | 仮確保を解除。残高そのものは減らない | 仮確保中は利用可能枚数が一時的に減る |
| 消費確定後、サーバーの開始認可前に失敗 | 未使用ならrelease要求で1枚返却。届かなくても予約期限後の再訪問・残高確認で回収 | 期限内の即時返却や、訪問せずに返却されることは保証しない |
| サーバーが開始を認可 | 1枚消費 | 映像の描画成功・ユーザーの最初の入力・READY解除を課金確定条件にしていない |
| 開始認可後に応答が届かない | 使用済み予約は自動返却しない | クライアントは開始確認待ちとして扱う。エラー表示だけで返却済みと判断しない |
| プレイ中・消費済みREADY・一時停止中の明示退出 | 返却なし | 既存の退出確認に従う。ゲーム終了やクリアによる返却もない |
| 終了後に再挑戦 | 新しい予約で1枚消費 | 古い予約は再利用不可。開始確認でキャンセルすれば追加消費なし |
| 接続切れ・ページ再読込 | 切断だけで自動返却しない | 同一プレイの復帰と新規プレイを区別。復帰可能性を無条件に保証しない |
| 対戦・協力の直接要求 | 拒否、消費なし | 無料ベータ対象外。[提供モード制限](free-beta-play-modes.md)参照 |

## サーバーの境界と二重操作

1. 予約は所有者・ゲーム・筐体・モードに紐付く。ソロ予約の期限は作成から2分。
2. captureで消費台帳を作成し、WebSocketのstartSoloで利用記録を作って開始認可する。DB上のplay_sessionsがplayingでも、利用記録なしならまだ認可前の場合がある。
3. 同一予約のcapture再送は1回だけ消費。同一予約の未使用capture返却は1回だけ。利用記録と返却の競合は条件付きSQLとDB batchで排他する。
4. HTTP 200だけで開始成功とは判定しない。released等の既存状態を200で返す場合があり、クライアントはcaptured状態を確認する。
5. 二重クリックで別々の予約が作られた場合まで「同一予約の冪等性」で無料にはしない。新しい予約IDは別の取引として扱う。
6. 期限切れの未確定予約は利用不可。定期保守はactive予約をexpiredにするが、使用済み・未使用を問わずcaptured予約を一律返却する処理ではない。

実装: `apps/web/src/features/platform/play-service.ts`、`apps/web/src/worker/platform.ts`、`apps/web/src/worker/credit-reservations.ts`、`apps/web/src/worker/cabinet-room.ts`。

## 返却要求が届かなかったときの回収

Issue #31で、bootstrap・残高確認・新規予約前に行うクレジット整合へ回収を追加する。

- 本人のソロ予約だけを対象とする。期限切れ・captured・開始の利用記録なし・所有者/通貨/金額/プレイに一致する消費台帳あり、をすべて満たす必要がある。
- 有効期限内は開始要求が到着する可能性があるため回収しない。期限判定は開始認可と同じD1側の日時比較を使う。期限切れ予約を再利用して始めることはできない。
- 既存の冪等な返却台帳を使い、返却要求との競合でも二重返却しない。利用済み予約は、READY・一時停止・応答欠落・明示退出であっても回収しない。
- 日次補充より前に回収する。例えば5枚から未開始captureで2枚になっていた場合、3枚返して5枚に戻し、さらに日次補充を上乗せしない。
- 1回につき最大20予約。残りは次の整合時に扱う。全筐体の走査、Cronの追加、無制限の再試行はしない。DB障害時はエラーを返し、その要求で補充だけを続行しない。再訪問・残高再確認で再試行する。
- 回収を含む残高整合の失敗は既存のdaily_credit失敗計測に含める。新しい通知ポリシー・閾値は追加しない。返却成功は新しい無料特典の付与とは区別する。
- 開始SLIの過去の応答欠落記録は書き換えない。返却できたことを、開始許可が届いた証拠として扱わない。

## 問い合わせ時の運営手順

- PULBASEのX窓口へ、発生日時（タイムゾーン）、ゲーム名、プロフィールのPlayer ID、筐体URL、エラー内容を連絡してもらう。Cookie・認証トークン・Googleのパスワードは求めない。公開投稿ではなくDMで受け付ける。
- 予約・消費台帳・返却台帳・利用記録・開始応答の監視を照合する。利用記録なしでcapture済みなら未開始返却の調査対象。利用記録ありは応答欠落と描画失敗の可能性を含めて調査し、自動返却の対象とはしない。
- 日次補充・登録特典が同時に発生し得るため、画面の残高差だけで二重消費と断定しない。
- 原因不明のまま台帳や利用記録を直接削除しない。本人確認・理由付き補正・監査履歴の運営機能はEN-06の残課題。今回の自動回収は上記の未使用ソロ予約に限定し、使用済みプレイへの補償や手動SQL補正は導入していない。

## 検証と残課題

- 3ゲーム共通で同一予約の並行capture/release、未確定キャンセル→別予約で再挑戦、認可と返却の競合を自動テストに追加。既存の所有者・期限・再利用防止テストも維持。
- クライアントの予約失敗、capture失敗、開始失敗、返却失敗、応答欠落時の通知状態を回帰テストで確認する。
- ローカルの対象44テスト、全865テスト、型検査・検証用ビルドが成功。最終CIと検証環境の実残高・開始・観戦・退出の結果は[Issue #28](https://github.com/papettoTV/virtual_gamecenter/issues/28)に記録する。テスト用ゲストのみ使用し、通常ユーザーの残高を操作しない。
- Issue #31の追加検証は3ゲームの再訪問/残高確認/新規予約前の回収・再返却拒否、未期限/他人/使用済み/別モード/不整合台帳の除外、1回20件、日次補充との並行実行、回収DB障害時の補充停止と匿名失敗計測。ローカル全883テスト・型検査・検証用ビルド成功。CI・検証反映SHA・実際の期限経過による残高確認は[Issue #31](https://github.com/papettoTV/virtual_gamecenter/issues/31)と専用PRに記録する。
- 未訪問者のCron回収、開始認可後の描画失敗の補償判断、元のrelease要求そのものの自動再送、運営補正は残課題。今回の確認で解決済みにしない。
- 切断から2分以内の同一ソロ復帰分岐は存在するが、保留中の接続回復・負荷対策と全端末の検証を含めた保証はできない。[予約検証の初期記録](credit-reservation-validation.md)の復帰記述を無条件の保証として扱わない。
- OP-03は対応中。全体の完了・本番公開を意味しない。負荷試験は保留・未合格を維持する。
