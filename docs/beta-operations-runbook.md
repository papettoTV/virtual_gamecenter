# 無料ベータの監視と障害対応

更新日：2026-10-19

対象は購入停止中の無料ベータ。障害の発見から調査・停止判断・復旧確認までを扱う。現状は読み取り専用の疎通チェックと手動実行経路を準備した段階で、自動死活監視・通知の実着信・復旧訓練は未完了。本番公開の承認ではない。

## 監視の分担

| 対象 | 確認手段 | 現状 |
| --- | --- | --- |
| アプリの入口・配信JS・公開文書・全ゲームの筐体一覧 | `service:check` | ローカル検証と自動テスト。リモートの実行・通知は別途確認 |
| Workers・D1・DOの利用量と費用 | 既存の利用量監視とCloudflare通知 | 設定・検証記録は `cloudflare-usage-monitor.md`、`cloudflare-cost-alerts.md` |
| ゲーム開始・クレジット付与・ログイン | 専用テスト利用者による主要導線確認、Workerの既存エラーログ | 疎通チェックの成功だけでは確認できない。失敗率の集計・通知は残課題 |
| 観戦の遅延・再接続 | 2端末の短い手動確認 | 長時間負荷試験とは分ける |
| 保存・削除処理 | 既存Cron・削除証跡と受付状況 | バックアップ復元時の再削除を含む実運用確認は残る |

## 読み取り専用の疎通チェック

`apps/web` で実行する。

```bash
npm run service:check -- --environment local
npm run service:check -- --environment staging
```

本番を確認する場合だけ、対象を明示して実行する。準備中ページの間はアプリ未稼働として失敗するのが正常であり、監視を通すために準備中ページを解除しない。

```bash
npm run service:check -- --environment production --confirm-production
```

- 検証は `develop.virtual-gamecenter.pages.dev`、本番は正規URLの `pulbase.com` に固定する。リモートURLの任意指定・リダイレクト追従を禁止する。
- ローカルだけ `--origin http://localhost:5174` 等でloopbackのポートを変更できる。
- Basic認証が必要なら、`PULBASE_CHECK_USERNAME` と `PULBASE_CHECK_PASSWORD` を環境変数で渡すか、Git管理外のJSONファイルを `PULBASE_CHECK_AUTH_FILE` で指定する。JSONの項目は `username` と `password`。値をコマンド引数・資料・Git・レポートへ書かない。
- `.dev.vars` に上記2変数を保存した場合は、`node --env-file=.dev.vars --experimental-strip-types scripts/service-check.mjs --environment staging` で明示的に読み込む。通常のコマンドは秘密ファイルを自動探索しない。
- 各要求のタイムアウトは10秒。現在の3ゲームでは1回最大7要求（HTML、JSのHEAD、筐体一覧3件、規約2件）。取得本文は1件512KiBまで。再試行・並列・ループは行わない。
- Cookie・bootstrap・ログイン・クレジット仮確保・筐体作成・WebSocketは使用しない。通常のアクセス制限カウンタやアクセスログは発生するが、プレイヤーや残高・プレイ履歴は作らない。
- レポートは環境、検査名、成否、HTTP状態、所要時間、固定の失敗分類のみ。認証値・応答本文・筐体ID・プレイヤー名・生の例外は出さない。
- 終了コード0は指定した読み取り検査の成功に限る。購入停止、OAuth、特典、ゲーム開始、ライブ映像の品質を保証しない。

## GitHubからの確認

`.github/workflows/service-check.yml` は手動実行専用。develop以外では実行しない。検証専用のBasic認証をGitHub Secretsの `PULBASE_CHECK_USERNAME` / `PULBASE_CHECK_PASSWORD` に登録してから実行する。Cloudflare APIトークンやGoogleの秘密鍵は渡さない。

自動スケジュールは未設定。Actionsの失敗通知はGitHubの個人通知設定に依存するため、ファイル追加だけでメール通知済みとは扱わない。自動化前に、通知先と当番、頻度、失敗・復旧の実着信を確認する。

## 内部目標の案

利用者向けSLAではなく、小規模ベータの運営判断用の暫定案。運営者の確認と計測準備が必要。

| 指標 | 暫定目標 | 判定上の注意 |
| --- | --- | --- |
| 定期疎通の成功率 | 月間99%以上 | 全予定実行が分母。未実行・通知基盤停止を成功にしない。現在は定期実行未設定 |
| ゲーム開始成功率 | 仮確保後の開始98%以上 | 利用者の中止・残高不足・明示的な制限を別分類。現時点では集計未実装 |
| 死活監視の発見 | 5分間隔、連続2回失敗で通知 | 再試行で負荷を増やさない。3回連続正常で復旧通知。まだ自動化していない |
| 障害の初動 | 対応可能時間内30分を目安 | 一人運営で24時間即応は保証しない。重大な残高・漏えい疑いは優先 |
| 復旧判断 | 4時間を超える見込みなら停止継続・状況案内 | 根拠のない復旧時刻を約束しない |

## 障害時の手順

1. 発生時刻（日本時間とUTC）、環境、対象リビジョン、失敗した検査名・状態コードを記録する。Cookie・認証情報・利用者の生ログは貼らない。
2. 401/403は監視用認証や環境指定の問題と一般障害を分ける。429は乱用対策や枠不足を疑い、上限引上げ・連打・自動リトライで通そうとしない。
3. アプリだけの障害か、D1・DO・ログイン・配信経路のどこかを確認する。既存の利用量監視も照合する。無料枠超過と基盤障害の因果を推測で確定しない。
4. 残高の不整合・データ漏えい・ゲーム開始後の即切断が続く場合、新規開始を止める判断を運営者へ求める。main、DNS、認証、公開用bindingの変更・準備中ページへの切替は明示的な承認を得て行う。閲覧だけ可能なら観戦・案内を残す選択肢も検討する。
5. 台帳を直接加算して帳尻を合わせない。仮確保、消費、開始記録を確認し、返却の可否・重複を調査する。理由付き補正と監査記録の運営手段はEN-06で整える。
6. 前版へ戻す場合、アプリとDBスキーマの互換性を確認する。Workerの巻き戻しでDBも戻ったと考えない。DB復元前は書き込み停止・独立R2削除証跡の保全・復元後の再削除を確認する。具体手順は `data-retention-and-deletion.md` と `production-environments.md` を参照。
7. 復旧候補を検証環境で確認する。疎通に加え、専用テスト利用者の開始・観戦・ログイン・残高保持を確認する。準備中ページや購入停止を解除してよいかは別の公開判断とする。
8. 復旧後は原因、影響時間、利用者影響、対応、未解決事項を記録する。問い合わせ窓口はX `@pulbase`。公開連絡に利用者情報や内部エラー本文を載せない。

## 次に残る実施事項

- GitHub Secrets・通知設定、検証環境での正常/失敗/復旧通知の実着信。
- ゲーム開始・付与・ログインの失敗率集計と通知。死活チェックと区別する。
- 検証専用DBでの復元・削除再適用訓練。本番DBの復元や削除は別途承認する。
- 実機の主要導線・素材の権利・本番専用環境の確認。
- 長時間負荷試験は未合格の残課題として保留。他作業の完了や公開可否の承認と混同しない。
