# 任意のフィードバック

Issue #37 / 2026-10-25。利用者からの感想・不具合報告を、ログインやメールアドレスなしで受け付ける。投稿や登録をプレイ条件にせず、クレジット特典には結び付けない。

## 案内タイミング

- アプリ共通フッターの「感想・不具合を送る」から任意に開ける。フッターはゲーム固有の読み込み・プレイ画面とは別に配置し、3ゲームの読み込み失敗時も利用できる。デモ埋め込み・開発用撮影モードでは表示しない。
- 3ゲームのプレイヤー用終了画面にも同じ「感想・不具合を送る」を置く。すべてリトライ等の後に共有と並ぶ補助リンクから開ける。閉じても結果・ランキング入力状態を維持する。DOT WAVEの途中ステージ終了と観戦者の結果にはプレイヤー用ボタンを出さない。
- 初めて終了したプレイからゲーム一覧へ戻った後に案内する。ランキング入力やリトライの選択中には出さない。初回案内済みなら、その後のプレイ終了で繰り返さない。
- 観戦では、画面が表示され、ゲームが進行中の時間を累計60秒以上見てからゲーム一覧へ戻った場合に案内する。READY・一時停止・終了・背景タブの時間は除く。
- 自動案内はブラウザごとに日本時間の1日1回まで。送信成功後は7日間出さない。手動表示はこの制限に含めず、同じ復帰時に手動表示した直後の自動表示は打ち切る。
- ゲーム内で手動表示した場合も、その滞在からトップへ戻った直後の自動案内を打ち切る。未送信で閉じた場合も同じで、ページ再読込を伴う復帰でも再案内を予約しない。手動表示だけで将来の別の滞在まで永久に抑制しない。
- 別モーダルが開いている間、プレイ中、観戦中には自動表示しない。再び別画面へ移動したら保留中の案内を取り消す。
- 頻度情報をlocalStorageに保存できない、または壊れている場合は自動案内を控える。手動送信は維持する。
- 再読込を伴うトップ復帰にも対応する。sessionStorageにゲーム・利用区分・時刻だけを一時保存し、5分以内の復帰で一度だけ読む。本文は保存しない。

自動案内は既存の共通 `liveSharing` の役割・進行状態とルート変更から判定する。手動の終了画面ボタンは共通コンポーネントを各結果画面に配置する。案内済み状態は端末間で共有しない。

## 入力・送信

種別「よかった」「気になった」「不具合」と、1〜2,000文字の本文。対象ゲームと「プレイ / 観戦 / サイト利用」、プレイヤー名・端末/ブラウザ種別の記録を送信前に案内する。表示名は有効セッションからサーバーが取得する送信時点のスナップショットで、本文に混ぜず別列に保存する。メール、プレイヤー/アカウントID、筐体ID、現在URL、端末の詳しい情報は保存しない。本文に個人情報・秘密を記入しないよう案内する。返信機能はない。

×・Escape・モーダル外クリックで閉じる。閉じるだけなら入力は同じページ内で保持するが、ページ再読込では失われる。送信失敗時は内容を残し、再送できる。同じ内容の再送には同じ投稿IDを使い、二重保存を防ぐ。成功通知は既存の共通通知（5秒・×付き）を使用する。

`POST /api/feedback` は同一Origin・JSONのみ。8KiBまで読み込み、宣言済み項目・ゲーム・種別・利用区分を検証する。共通の分散/要求制限に加え、同じ接続元からUTCの1日20件までとし、共有回線の少人数利用を妨げにくくする。拒否は429、同じIDで別内容は409、保存障害は503。同一内容の再送は追加枠を消費しない。入力本文や内部例外をログ・エラー応答に出さない。

## 保存・運営確認

- D1 `feedback`：投稿ID、種別、本文、ゲームID、利用区分、日時、投稿時の表示名、端末/ブラウザ種別。90日を過ぎたら既存の定期保守で削除する。
- `feedback_rate_buckets`：日替わりのIP由来ハッシュ、件数、最終投稿ID。記録から1日で期限、既存の定期保守で削除する。本文に連投対策キーを関連付けない。IPハッシュも保護対象であり、完全匿名を保証するものではない。
- アカウントIDを保存しないため、退会による自動削除とは連動しない。個別の削除相談は既存のX窓口へ。同名を理由に他人の投稿を削除せず確認する。投稿者の確認が困難な場合もある。
- `/operator/feedback` と `/api/operator/feedback` を提供する。stagingは現行の運営者画面と同じく、Googleログイン済み・許可アカウント・有効セッションを毎要求で確認し、失効・退会・権限除去を拒否する。ローカルは以下の開発者限定条件で利用できる。本番では引き続き無効。
- 運営者画面からリンクし、直近90日を新しい順に1ページ50件表示。本文をHTMLエスケープし、no-store・noindex・CSPで保護する。CSV出力・外部通知は追加しない。

## ローカルで送信済みの内容を確認する

一覧の日時は `Asia/Tokyo` の日本時間（JST）で表示する。DBとJSON APIの `created_at` は従来どおりUTC。プレイヤー名・端末/ブラウザは新規投稿から記録し、0025以前の投稿は「未記録」とする。過去のログや現在のアカウント情報から推測して補完しない。端末/ブラウザは最大1,024文字のUser-Agentをその場で分類し、原文は投稿に保存しない。iPadのデスクトップ表示やUser-Agent変更などで誤判定し得る推定情報として扱う。判別できない新規投稿は「不明」。セッションのない投稿の名前は「未記録」。

1. フィードバック実装済みの作業フォルダの開発サーバーを起動し、Macのブラウザで `http://localhost:5174/` を開く。
2. 右上のプロフィール → 「ユーザー登録で名前を変更」を選ぶ。必要なら利用規約への同意・プライバシーポリシーの確認を本人が行う。
3. 登録画面の **「開発者ユーザーでログイン」** を選ぶ。「Googleで登録」ではない。すでに開発者ユーザーならこの操作は不要。別アカウントでログイン中なら、自分でログアウトしてから行う。
4. 同じブラウザで **`http://localhost:5174/operator/feedback`** を開く。直近90日の内容が新しい順に表示される。新しい投稿の確認はページを再読み込みする。

JSON確認用は `http://localhost:5174/api/operator/feedback`。同じ有効セッションが必要で、URLだけを別ブラウザに渡しても閲覧権限は移らない。`localhost` と `127.0.0.1` はCookieが別になるため、ログイン時から同じホスト名を使用する。投稿時のホストが異なっていても、同じ作業フォルダのローカルD1への投稿なら一覧に表示される。

条件は `APP_ENV=local`、`DEVELOPER_AUTH_ENABLED=true`、ループバックURL（localhost / 127.0.0.1 / IPv6ループバック）、有効な `local-developer` 固定IDの開発者セッション。既存のローカル設定で有効なので、運営者用のSecret追加は不要。ゲスト、Googleだけのアカウント、別IDの開発者、期限切れ・ログアウト・削除処理中は拒否する。LANのIPを使った運営者URLは対象外。開発サーバーをインターネットへ公開しない。

未ログインは401でログイン案内、権限違いは403、環境・URL・開発者認証設定が対象外なら404。stagingのGoogle許可リスト条件は緩和せず、本番で開発者認証フラグを設定してもこの経路は利用できない。ローカル画面は検証・本番の投稿を読み込まない。`/operator/operations` の集計画面は今回ローカル対応していない。

### 2026-10-27 LANのHTTP接続で送信中のままになる問題（Issue #56）

スマホからHTTPのLAN URLを使用した際に、送信準備中の `crypto.randomUUID()` が利用できず例外となった。さらに、その呼出しがtry/finallyの外にあったため、送信中フラグとボタンが解除されなかった。localhostでの従来の画面テストでは発見できていなかった。

既存の共通 `createUuid()` に切り替え、UUID生成とペイロード準備もtry/finallyの中に移した。通常のHTTPでは利用できない `randomUUID` の代わりに `getRandomValues` を使える互換経路を使用する（[randomUUIDの条件](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/randomUUID)、[getRandomValuesの条件](https://developer.mozilla.org/en-US/docs/Web/API/Crypto/getRandomValues)）。サーバーのUUID検証・再送の同一ID・認証・制限は維持。UUID準備自体が失敗してもエラーを出して本文を残し、「送る」に戻す。

修正前にrandomUUID未提供のスマホ幅テストで停止を再現し、修正後はPC/スマホ幅の計14件が成功。全957アプリテスト・型検査・検証用ビルドも成功した。Macのアプリ内ブラウザで実際の `http://192.168.0.20:5174/` から合成の確認用投稿を1件送信し、成功通知とlocalhostの運営者一覧への保存を確認。実iPhone Safariの再確認は利用者に依頼し、Mac上の確認を実機合格とは扱わない。
